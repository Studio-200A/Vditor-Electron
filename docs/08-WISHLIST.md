本文档记录尚未排入当前版本承诺的功能设计。条目进入具体版本计划前，不应视为已承诺实现。

## 跨平台进入条件

当前至 0.2.6 的开发与实机验证以 Linux 为准。涉及文件系统、窗口集成、系统快捷键或发行打包的愿望条目，统一遵循 [`docs/04-CROSS-PLATFORM.md`](04-CROSS-PLATFORM.md) 的边界和验证要求。

## GitHub Actions 云端构建与交付

状态：云端质量检查已于 0.2.5 批次 10 落地（`.github/workflows/quality.yml`：在向 `main` 的 push/PR 上执行 format、项目元数据、lint、renderer build、main/renderer typecheck、Vditor 锁定检查与单元测试，不含发布权限）；自动构建/交付仍暂缓。

- 在交付自动化落地之前，发布准备继续以本地 `check:all`、本地候选包构建和人工冒烟验证为依据；CI 质量检查不替代 Electron E2E 与打包验证。
- renderer 需要差异时消费主修饰键、窗口控制或标题栏安全区等具体能力，不把 `process.platform` 判断扩散到功能控制器。
- 涉及路径 URL、本地资源、递归遍历或文件改名时，计划必须覆盖 Windows 盘符、大小写不敏感卷、符号链接、保留文件名和文件占用等语义。

## 平台快捷方式文件支持

状态：暂缓，不纳入 0.2.0。

Windows `.lnk` 与 macOS Finder alias 是平台快捷方式文件格式，而不是可由 Node `realpath` 统一处理的目录链接。当前目录树仅支持真实路径可解析的目录链接（symlink 与 Windows junction）；`.lnk` 和 Finder alias 继续按普通文件处理。

未来若支持，必须单独定义：平台专用目标解析与失败行为、目标在工作区内外的授权判断、循环与不存在目标处理、链接图标/tooltip/无障碍文案，以及 Windows 与 macOS 实机验证。不得把快捷方式解析结果直接当作已授权的本地资源路径。

## SVG 图片安全性与受控栅格化

> **背景（已交付）：** `allowSvgImages` 显式开关已随 0.2.0 上线（见 CHANGELOG「feat(controlled SVG rendering)」）。下方第一段描述该开关当前的运行时行为，仅作背景；本节保留的未承诺设计是「受控栅格化」服务。

SVG 渲染开关默认关闭，并同时约束受控本地资源与主窗口 HTTP(S) 图片：本地 `.svg` 只有开启后才以 `image/svg+xml` 响应；远程 `.svg` URL 在请求前拒绝，无扩展名但响应 `image/svg+xml` 的图片在响应头阶段拒绝。关闭权限时会使已缓存图片重新经过策略。该开关不是对不受信任 SVG 的安全保证：协议仍保持受控根、`X-Content-Type-Options: nosniff` 与 `Cache-Control: no-store`，CSP 仍不向 `local-file:` 开放脚本、连接、`object` 或 `iframe` 能力，导航和弹窗策略也不得放宽，也不会完整解析或过滤 SVG 内容。

### 观察 Loupe 得到的启发

GNOME Loupe 是专门的原生图片浏览器。其源码按 MIME 识别 `image/svg+xml` 与压缩 SVG；SVG 走独立解码路径，通过 glycin/librsvg 按视口分块请求已经栅格化的 frame/texture，而不是将原始 SVG 当网页嵌入 UI。它还具备请求取消、librsvg 尺寸上限和按打印目标尺寸重新渲染 SVG 的处理。Loupe 将可扩展图片解码置于 sandboxed glycin 体系中；这种“将不受信任格式解释与应用 UI 隔离”的方向，比单靠格式黑名单更具长期价值。

### Vditor Desktop 的合理借鉴边界

- 不在当前 Electron renderer 中尝试复刻 Loupe 的 GTK/glycin/librsvg 栈，也不因 SVG 支持引入原生解码子进程或跨平台二进制依赖；这需要独立处理打包、资源限额、取消、错误模型、Windows/macOS 支持与安全审计。
- 近期继续采用用户显式开关和真实 Electron 回归：普通 SVG 在三种编辑模式及 HTML/PDF 导出中的兼容性；关闭后立即拒绝；包含脚本、事件属性、`foreignObject`、导航、弹窗与外部引用的 SVG 不得取得执行、导航、外连或越界读取能力。
- 若未来需要“默认安全地预览 SVG”，应单独设计主进程受控栅格化服务：验证文件身份和受控根后，在隔离的受限解码环境中将 SVG 转为 PNG 或等价像素结果，再把结果交给 renderer 和导出流程。renderer 不取得原始 SVG 的可执行文档能力。
- 该后续专题应按内容/MIME（包括 `image/svg+xml-compressed`）而非单纯扩展名判断，定义 SVG/压缩 SVG 的大小、像素、复杂度与超时上限，并覆盖取消、损坏文件、打印/导出、内嵌和外部资源、三平台打包和实体机验证。

## 编辑区拼写检查

状态：候选设计，尚未排入版本承诺。实施与关闭条件统一跟踪于 [`00-ISSUES.md`](00-ISSUES.md)「P3（功能完善）」的编辑区拼写检查条目；本节描述拟议功能与验收边界。

### 1. 调查依据与目标

2026-10-04 调查确认：Electron 内置 Chromium 拼写检查从 Electron 9 起默认开启；字体设置输入框出现红色波浪线，是字体名称被作为普通单词检查，不是应用新增的语法检查功能，也没有证据证明这是 Electron 44.5.1 特有的回归。当前修复在主窗口创建后调用 `session.setSpellCheckerEnabled(false)`，明确关闭检查引擎。

本项目锁定的 Vditor 3.11.3 在 SV、IR、WYSIWYG 三种模式的编辑元素上均设置 `spellcheck="false"`（`node_modules/vditor/src/ts/{sv,ir,wysiwyg}/index.ts`），未发现公开的拼写检查配置选项。因此未来需要同时开启 Electron 引擎和编辑元素的检查属性；只开启其中一层不能构成完整功能。

本地 MarkText 源码（提交 `2930c666`）提供了分层参考：`packages/desktop/src/main/spellchecker/index.ts` 管理 Electron 检查引擎、语言和用户词典；Muya 的 `spellcheckEnabled` 选项控制编辑根元素，代码块和行内代码等单独使用 `spellcheck="false"`；右键菜单从 Electron 的 `context-menu` 事件获取建议词，再传回 Muya 的 `replaceCurrentWordInlineUnsafe()`，通过编辑器自身的文本更新路径纠错。该方法确认光标附近的词仍匹配原词才替换；现有测试覆盖 Markdown 更新、光标位置和不匹配时不修改，但本次未运行 MarkText，也未验证其真实 Electron 纠错撤销及跨平台行为。

目标是在普通 Markdown 编辑中提供用户主动开启的单词拼写检查、原生错误标记和右键纠错。首期不承诺语法检查、中文病句检查、AI 改写、全文自动纠错或云端服务；不更换 Vditor 编辑引擎。

### 2. 设置与用户体验

- 设置页面「编辑器」下增加拼写检查分组，默认关闭；旧配置缺少字段时保持关闭，不因升级自动启用。
- 拟议持久化字段：`spellcheckEnabled: boolean`、`spellcheckLanguage: string`（`system` 或受支持语言代码）、`spellcheckShowMarks: boolean`（默认 `true`）。语言代码必须由主进程依据实际支持列表验证；字段名与 TOML 分组在进入版本计划时按当前设置模型最终确认。
- Linux/Windows 可选择一个检查语言，`system` 解析为系统区域对应的可用语言；没有匹配词典时明确提示用户选择，不静默改成无关语言。macOS 使用系统拼写检查和自动语言识别，不显示无效的应用语言选择器。
- 「显示拼写错误标记」与「启用拼写检查」分别控制。启用检查但隐藏波浪线时，右键建议仍可用；仅关闭检查引擎才停止检查。隐藏标记的 CSS 能力需先验证当前 Chromium 与各主题的实际效果。
- 检查只作用于可编辑正文；设置中的字体名称、文件路径、搜索框、重命名框等应用输入区明确保持 `spellcheck="false"`。预览和导出不带拼写标记。
- 右键错词时，在既有菜单中加入建议词和「加入用户词典」；无建议时给出本地化说明。提供用户词典列表及删除条目入口，明确词典作用于应用共享 session，而非单个文档。
- 所有开关、语言说明、菜单及错误提示同步提供 `en_US`、`zh_Hans`、`zh_Hant`。开关和语言切换即时生效，不重建全部编辑器，也不改变文档内容或修改状态。

### 3. 检查范围与 Markdown 边界

目标覆盖 SV、IR、WYSIWYG 中的正文、标题、列表、引用和表格文字。排除代码块、行内代码、公式、链接目标、图片资源地址及 HTML 语法；链接显示文字仍可检查。MarkText 的排除策略依赖 Muya 自有 DOM，不能直接照搬到 Vditor。

进入版本计划前必须按 Vditor 3.11.3 的实际结构验证这些区域是否可稳定区分，尤其是 SV 中源码与正文混排、IR 中活动语法展开以及输入后 DOM 重建的情况。排除规则及重应用只能位于 adapter；不能通过全文重写、重建编辑器或在业务层散落私有选择器来实现。某种模式无法可靠排除时，应在版本计划中明确限制支持范围，再决定是否交付；不得把原生检查描述为理解 Markdown 的语义检查。

### 4. 分层实现与纠错交易

| 层级 | 拟议职责 |
| --- | --- |
| 主进程 | 管理 session 检查开关、语言、词典供应和用户词典；接收 Electron 右键事件，构建建议菜单；验证 renderer 来源及跨进程参数。 |
| preload / shared contracts | 暴露设置语言、获取支持语言及管理用户词典等有具体产品需要的窄接口，提供可恢复的稳定结果类型；不暴露通用 Electron/session/IPC 对象。 |
| `renderer/settings/` | 拥有设置 UI、持久化及运行状态反馈，区分用户希望开启与词典实际可用，避免界面显示已启用而引擎不可用。 |
| `renderer/editor/` | 协调活动 tab 的纠错请求与编辑器生命周期，绑定请求到原 tab、编辑器实例和目标词；在菜单期间切换文档、模式或重建后使旧请求失效。 |
| `vditor-adapter.js` | 提供拼写开关、区域排除及必要的选区/纠错语义接口；集中所有 Vditor 私有结构依赖，在初始化、模式切换及重建后重新应用。 |

`app-composition.js` 仅增加必要的构造、依赖注入和窄协调接线，不承接词典状态、事件监听或私有 DOM 操作。Electron session 为共享能力，开关由单一设置流程管理，不允许每个 tab 独立开关共享引擎。

纠错实现先做最小原型：验证 Electron `webContents.replaceMisspelling()` 是否在三种模式中正确触发 Vditor 输入、Markdown 序列化、修改状态及撤销/重做。若不能满足契约，再评估由 adapter 恢复目标选区并调用 Vditor 已有的局部编辑路径；Muya 的文档模型更新方法不能移植为 Vditor 的实现。不得采用全文 `getValue()/setValue()`、直接改写内部 DOM 或另建撤销栈来纠错。

执行建议词前验证请求所属 tab、编辑器实例、目标范围与原词仍有效。菜单打开后发生输入、切换或重建时，无法确认目标则取消请求，不凭当前光标替换其他词。替换应表现为一次可撤销的局部编辑，保留周边格式，更新修改状态，并将焦点与光标返回正确文档。加入词典只更新词典，不应改变文档或制造一次文本撤销操作。

新增 adapter 接口同步 frozen facade、类型声明和导出契约测试，并把三种模式的结构假设与验证项目写入 `docs/07-VDITOR-UPGRADE.md`。监听器、观察器、菜单请求和保存的选区引用均需有 tab 关闭、重建、窗口关闭时的释放或失效路径。

### 5. 离线、词典与平台行为

根据 [Electron 官方说明](https://www.electronjs.org/docs/latest/tutorial/spellchecker)，Windows/Linux 使用 Hunspell，macOS 使用系统检查服务；内置检查本身不向 Google 发送输入内容，但 Windows/Linux 的词典默认从 Google CDN 下载。不能把默认方案宣传为首次使用也无需联网。

拟议首期优先随包提供经许可证与分发方式验证的英文词典，确保全新配置、断网启动仍可检查英文；其他语言只展示实际可用状态，不承诺已离线提供。实施前验证 Electron 44.5.1 支持的词典供应/初始化方式和三个平台的包内资源路径，不预设 `file://` 可直接作为下载端点，也不临时启动未设计的本地服务。若无法可靠随包供应，应先明确替代方案与产品范围，再进入版本承诺。

不默认添加后台下载，不自动下载全部语言。未来扩展词典下载时需另行设计用户主动触发、来源和完整性校验、失败重试及离线状态。用户词典继续由主进程管理，并说明其 Chromium 数据目录归属；TOML 只保存偏好，不复制 Electron 的内部词典或混用配置目录。

### 6. 实施进入条件与验收

先完成三种模式的最小 Electron 原型，证明原生标记、区域排除、右键纠错和撤销链可兼容 Vditor，再确定正式支持范围和排期。原型不满足要求时保留研究结果，功能保持默认关闭，不以单个 HTML 属性测试代替编辑器集成验收。

- 单元/DOM 测试：配置默认值与旧配置、IPC 语言/词典参数校验、adapter 结构契约、初始化/模式切换/重建后属性保持、区域排除、过期纠错请求拒绝及资源清理。
- 真实 Electron E2E：三种模式的错词建议和替换结果、格式保持、`getValue()`、保存重开、修改状态、撤销/重做；菜单期间输入或切换 tab 后不误改；加入词典不修改文档，删除词典项后恢复检查。
- UI 验证：编辑区开启后字体/路径等应用输入仍不标红；隐藏标记仍有建议；预览与 HTML/PDF 导出不带标记；浅深主题、缩放、输入法及混合语言行为合理。
- 离线与平台验收：全新配置下断网启动的词典供应、缺失/不可用语言反馈和用户词典重启恢复；Linux、Windows、macOS 分别完成实机验证，不以 Linux 结果替代另外两平台。
- 大文档连续输入、多 tab、开关热更新和重建后无明显输入延迟、重复监听或选区丢失。实施涉及两进程与 renderer 时按项目要求完成干净完整构建、`check:all`，词典随包供应另做对应平台打包验证。

## 浮动工具栏与工具栏模式

当前实现仍是固定的 Vditor 工具栏，通过应用菜单「Vditor Desktop」→「布局」→「显示工具栏」（`toolbarVisible`）显隐控制；0.2.0 开发 tracker 批次 7 已完成的是工具栏加载占位、mount 交接和边界视觉稳定性修复，并不等同于本节的浮动工具栏功能。本节继续作为未承诺的后续设计保留。

浮动工具栏方案暂缓，待编辑器顶部空间、Vditor 工具栏兼容性和跨平台交互方案进一步验证后，再纳入具体版本计划。设计目标是让用户可以在“完整工具栏”“选区浮动工具栏”和“隐藏工具栏”之间选择，同时不改变现有 Markdown 编辑行为。

### 1. 目标界面结构

完整工具栏模式：

```text
标题栏： [侧边栏] │ 文件 编辑 视图 帮助      文档名      窗口按钮
工具栏： [新建][打开][保存] │ Vditor 内置工具栏
标签栏： [文档一][文档二][+]
编辑区
状态栏
```

选区浮动工具栏模式：

```text
标题栏： [侧边栏] │ 文件 编辑 视图 帮助      文档名      窗口按钮
标签栏： [文档一][文档二][+]
编辑区：选中文字时显示浮动格式工具栏
状态栏
```

隐藏工具栏模式：

```text
标题栏： [侧边栏] │ 文件 编辑 视图 帮助      文档名      窗口按钮
标签栏： [文档一][文档二][+]
编辑区
状态栏
```

隐藏模式不显示固定工具栏或选区浮动工具栏，但菜单和快捷键仍然可用。

### 2. 标题栏调整

- 侧边栏开关应位于自定义 titlebar 左侧，并排列在文件、编辑、视图、帮助菜单之前。
- 使用明确表示“左侧面板”的图标，不继续使用容易被误解为汉堡菜单的图标。
- 侧边栏按钮与文件菜单之间保留适当间距或细分隔线。
- tooltip 显示“切换侧边栏（Ctrl/⌘+Alt+B）”及对应本地化文本；显示和交互均使用与平台对应的主修饰键，不得只改 native menu 而保留错误的 renderer 提示。
- 使用 `aria-label` 和 `aria-pressed` 表达用途及当前状态。
- 位于 Electron 可拖动标题栏时，按钮必须设置 `-webkit-app-region: no-drag`。
- 检查 Linux、Windows、macOS 布局；macOS 左侧窗口控制区域应预留安全间距。
- “视图”菜单中的“显示侧边栏”从“布局”子菜单提升到“视图”一级，并保留勾选状态和主修饰键快捷键（Linux/Windows 为 `Ctrl+Alt+B`，macOS 为 `Cmd+Alt+B`），避免与 Vditor 加粗冲突。

验收标准：固定工具栏隐藏后，鼠标用户仍可一键开关侧边栏；按钮、快捷键和菜单同步同一个 `sidebarVisible` 状态；重启后正确恢复状态。

### 3. 固定工具栏调整

固定工具栏左侧应用按钮为：

```text
新建 | 打开 | 保存 | Vditor 内置工具栏
```

- 删除固定工具栏中的侧边栏按钮。
- 保留新建、打开、保存及现有行为。
- 删除固定工具栏中的设置按钮，设置继续由状态栏入口、菜单和主修饰键加 `,` 访问（Linux/Windows 为 `Ctrl+,`，macOS 为 `Cmd+,`）。
- 应用按钮与 Vditor 工具之间保留清楚但不过度突出的视觉分组。
- 非完整工具栏模式下隐藏整个固定工具栏行，不留下空白高度或边框。
- 隐藏工具栏不得销毁 Vditor 实例、清空撤销历史或改变编辑模式。

### 4. 工具栏状态模型与设置

使用单一枚举替代互相约束的布尔字段：

```ts
type ToolbarMode = 'full' | 'floating' | 'hidden';
```

设置字段：

```ts
toolbarMode: ToolbarMode;
```

设置页面显示：

- 完整工具栏
- 选区浮动工具栏
- 隐藏工具栏

兼容旧配置时：

```text
旧 toolbarVisible = true  → toolbarMode = "full"
旧 toolbarVisible = false → toolbarMode = "hidden"
```

其他要求：

- 不把旧的隐藏状态自动迁移为浮动模式。
- 默认值为 `full`，保证首次安装时功能可发现。
- “重置布局”恢复 `full` 及其他布局默认值。
- 设置页面、视图菜单和实际 UI 使用同一个状态源。
- 切换工具栏模式即时生效，不重建所有 Vditor 实例。

建议的视图菜单：

```text
视图
├─ 显示侧边栏                         Ctrl/⌘+Alt+B
├─ 编辑模式
│  ├─ 所见即所得
│  ├─ 即时渲染
│  └─ 分栏预览
├─ 工具栏模式
│  ├─ 完整工具栏
│  ├─ 选区浮动工具栏
│  └─ 隐藏工具栏
├─ 布局
│  ├─ 显示标签栏
│  ├─ 显示状态栏
│  └─ 重置布局
├─ 设置                               Ctrl+,
└─ 全屏                               F11
```

### 5. 选区浮动工具栏功能边界

浮动工具栏是“选区格式工具栏”，不是完整 Vditor 工具栏的悬浮复制品。第一版只处理已选文字的格式化命令，建议包含：

- 粗体
- 斜体
- 删除线
- 行内代码
- 链接
- 在对应 Markdown 扩展开启时提供高亮

第一版不放入浮动工具栏的内容：

- 编辑模式切换、分栏显示切换
- 内容主题、代码主题
- 图片上传
- 表格、分隔线等光标位置插入命令
- 全屏、预览、导出等应用或视图控制
- 新建、打开、保存、设置和侧边栏按钮

空间不足时可以提供“更多”入口，但不应为了填满工具栏而加入与文本选区无关的命令。

### 6. 三种编辑模式的触发范围

- 所见即所得模式：监听编辑区域原生选区变化，浮动工具栏定位到选区上方或下方。
- 即时渲染模式：监听源码编辑器选区，格式化命令作用于当前 Markdown 文本选区。
- 分栏预览模式：浮动工具栏只绑定左侧源码编辑区，右侧预览区不重复显示。
- 选区为空、编辑器失焦、点击工具栏外部或按 `Escape` 时隐藏工具栏。
- 点击浮动工具栏按钮不能立即丢失选区；命令执行后恢复编辑器焦点。

### 7. 显示、隐藏和定位规则

- 选区长度大于零且编辑器处于活动状态时显示。
- 工具栏不能覆盖选区、窗口边缘、标题栏、标签栏或状态栏。
- 靠近顶部时自动放到选区下方，靠近底部时放到上方；水平位置在窗口内夹紧。
- 视口滚动、编辑模式切换、标签页切换、窗口失焦时重新计算或隐藏。
- 动画应短而克制，避免影响连续选择文字；隐藏时不能留下可点击的透明区域。
- 浅色、深色和 Monokai Pro Dark 主题下，浮动工具栏使用统一的应用主题变量。
- Linux、Windows、macOS 均需检查窗口边缘、缩放和高 DPI 下的定位；Windows 的显示缩放变化、macOS 的原生标题栏安全区和多显示器切换都不得依赖 Linux 的 CSS 像素假设。

### 8. 选区保持与命令执行

- 在执行命令前保存 `Range` 或编辑器的起止偏移量。
- 按钮 `mousedown` 阶段阻止默认失焦行为，避免选区消失。
- 命令执行后更新 Vditor 内容、撤销栈和修改状态，并将焦点还给原编辑器。
- 无法恢复选区时只隐藏工具栏，不修改文档内容。
- 每个浮动工具栏实例必须有明确销毁流程，避免标签页切换或编辑器重建时重复监听。
- 每个标签页销毁时释放 observer、事件监听和保存的 Range 引用。

### 9. 复用 Vditor 工具栏

优先复用 Vditor 已有命令和图标，但不要直接复制完整工具栏 DOM。建议通过适配层暴露窄接口：

```text
#vditorToolbarMount   Vditor 原生工具栏挂载点
#floatingToolbarMount 应用浮动工具栏挂载点
```

- Vditor 私有 DOM 查询和命令映射集中在 `src/renderer/vditor-adapter.js`。
- 业务代码不得散落新增 Vditor 私有选择器。
- 若上游 DOM 变化，只修改 adapter 和对应契约测试。
- 浮动工具栏按钮需补齐本地化 tooltip、键盘访问、焦点样式和 `aria-label`。
- 浮动工具栏相关逻辑不能继续无边界堆积进 `src/renderer/app/app-composition.js`；应将工具栏模式状态、浮动工具栏生命周期、选区保存/恢复和定位计算组织为边界清晰的模块或控制器。
- 将纯状态转换和几何定位计算写成可单元测试的纯函数。
- 不在多个模块各自注册相互竞争的全局 `selectionchange`、`click` 和 `resize` 监听器。
- 在 `docs/07-VDITOR-UPGRADE.md` 中补充浮动工具栏依赖的 Vditor DOM 契约和人工验证项目。

### 10. 验收测试

至少覆盖以下路径：

- 三种编辑模式下选择文字、显示、定位、执行粗体/斜体/链接并恢复焦点。
- 选区靠近窗口四边时工具栏不会溢出窗口。
- 滚动、切换标签页、切换编辑模式和点击外部后工具栏状态正确。
- 隐藏工具栏模式没有空白占位，菜单和快捷键仍然可用。
- 侧边栏按钮在三种模式下始终可达，按钮、快捷键和菜单状态保持同步。
- 设置重启后工具栏模式正确恢复，重置布局恢复完整工具栏。
- 单元测试覆盖：工具栏旧配置迁移与三态持久化、浮动工具栏状态转换和定位边界、选区失效条件。
- 浅色、深色、Monokai Pro Dark 以及 Linux、Windows、macOS 窗口布局下完成人工验收。

## 工作区文件名搜索

在资源管理器侧边栏提供搜索框，用于递归搜索当前工作区内的文件名。该功能仅搜索文件名，不建立索引、不搜索 Markdown 正文，也不改变现有按需展开的目录树行为。

### 1. 交互

- 搜索框位于资源管理器工具栏或工作区标题下方；未打开工作区时禁用。
- 输入后以约 150-250ms 防抖发起搜索；清空输入后恢复原目录树及其展开状态。
- 搜索结果使用扁平列表展示文件名和相对工作区路径，点击结果复用 `openPath()` 打开文件。
- 匹配规则为大小写不敏感的文件名子串匹配，沿用资源管理器的隐藏文件排除和可见扩展名过滤规则。
- 快速连续输入时，过期请求的结果不得覆盖较新的关键词结果；搜索中应提供轻量加载状态。

### 2. 主进程接口与边界

- 在 `src/main/services/file-manager.ts` 增加受限的递归文件名搜索接口，并经既有 preload 显式暴露给 renderer。
- 搜索根目录必须是当前已选择的工作区；解析每一个候选路径后验证其仍位于工作区根目录之内。
- 排除隐藏文件和隐藏目录，不跟随超出工作区的符号链接；沿用文件资源管理器已支持的扩展名过滤。
- 匹配和去重策略必须明确区分“搜索展示采用大小写不敏感”与“文件系统身份”；不得因 Windows/macOS 常见大小写不敏感卷而错误合并 Linux 上不同大小写的两个文件。
- Windows/macOS 支持进入范围时，补充保留文件名、无权读取目录、文件被占用和不同卷符/别名路径的错误与跳过策略。
- 接口返回相对路径、完整路径和文件名；不返回文件内容。
- 设置合理的结果数量与遍历数量上限，并在达到上限时返回可本地化的截断状态，避免超大目录阻塞主进程或 renderer。

### 3. Renderer 集成

- 搜索状态保留在 renderer 内存中，不写入会话或设置。
- 目录树的 `refreshTree()`、展开状态持久化和文件监听继续按现有逻辑工作；搜索只替换当前文件树的可见内容。
- 工作区切换、文件树刷新、扩展名设置变化或搜索框清空时取消/忽略旧结果并重新同步显示。
- 所有标签、提示、空结果和截断说明均通过 `src/renderer/locale/` 提供 `en_US`、`zh_Hans`、`zh_Hant` 文案。

### 4. 验收

- 嵌套未展开目录中的 Markdown 文件可被命中并打开。
- 隐藏文件、不可见扩展名和工作区外路径不会出现在结果中。
- 快速修改关键词、切换工作区和清空搜索后，结果不会闪回到过期状态。
- 大目录达到上限时界面保持可操作，并清楚提示结果可能被截断。

## 合并单元格表格支持

当前编辑体验计划中的表格行列操作仅面向普通 Markdown pipe table，不创建或编辑合并单元格。

思源笔记导出含合并单元格的表格时使用原生 HTML，而非 Markdown 表格扩展。例如：

```html
<table>
  <colgroup><col style="min-width: 60px;" /></colgroup>
  <tbody>
    <tr>
      <td colspan="2" rowspan="1">chart content</td>
    </tr>
  </tbody>
</table>
```

这说明合并单元格不能以普通 Markdown 表格的规则矩阵处理；后续支持需要同时处理 HTML `table`、`colgroup`、`colspan`、`rowspan`、跨行跨列网格定位、行列增删时的 span 调整、光标与撤销恢复，以及 WYSIWYG、IR、SV 三种模式的转换边界。

在具备完整设计、Vditor 兼容性验证和回归测试前：

- 不提供合并或拆分单元格功能。
- 对检测到 `rowspan`、`colspan` 或 `colgroup` 的 HTML 表格，不显示普通表格行列操作，或显示本地化的禁用说明。
- 不使用现有普通表格的新增/删除行列逻辑修改合并单元格表格，避免破坏 HTML 结构。
- 将该能力作为独立的后续表格编辑专题，而不是普通表格操作的顺带扩展。
