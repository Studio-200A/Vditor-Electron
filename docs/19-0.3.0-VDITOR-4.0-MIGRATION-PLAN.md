# Vditor-Electron 0.2.6 Vditor 4.0 升级计划

> 项目仓库：<https://github.com/Studio-200A/Vditor-Electron>
> 目标版本：`0.2.6`
> 前置基线：`0.2.5` 的当前稳定代码，Vditor 固定 `3.11.3`
> 唯一版本任务：升级 Vditor 至精确版本 `4.0.0`
> 上游参考：`/home/shawnzhang/Projects/vditor` 的 `v4.0.0` tag，以及 issue [#1319](https://github.com/Vanessa219/vditor/issues/1319)

## 1. 文档用途

本计划约束 0.2.6 的唯一工作：将 Desktop 从 Vditor 3.11.3 迁移到 4.0.0，同时保持本地优先 Markdown 文件、Electron 安全边界、文件保存/恢复/冲突语义和三种编辑模式。

这不是一次普通依赖更新。Vditor 4.0 将 SV 从私有 `contenteditable <pre>` 架构改为 `<textarea>`，上游同时明确放弃 SV 语法高亮和自动完成等能力。现有 `vditor-adapter.js`、SV 增强、样式与测试中的 3.11.3 DOM 假设必须逐项审计、重写、删除或降级；不得仅修改版本号和 selector。

计划定义目标、边界、迁移阶段和完成标准。实际进度、提交、验证证据和阻塞项只写入 [`docs/20-0.2.6-EXECUTION-TRACKER.md`](20-0.2.6-EXECUTION-TRACKER.md)。

## 2. 产品与迁移边界

### 2.1 必须保持

- 编辑普通 Markdown 文件，文件内容仍是唯一数据源；不引入私有格式、云同步、账户或遥测。
- WYSIWYG、IR、SV 三种模式，离线 bundled Vditor 资源，`contextIsolation: true` 与 `nodeIntegration: false`。
- 文件 identity、保存、自动保存、外部变化、恢复、watcher、TOCTOU 和本地资源协议契约；以 [`docs/06-FILE-SAFETY.md`](06-FILE-SAFETY.md) 为准。
- Vditor 私有 DOM 访问仍只存在于 `src/renderer/vditor-adapter.js`；业务 controller 不得为 4.0 增加散落 selector 或版本分支。
- 原生与自绘 caret 设置；SV 不能使用不可用的 Range 几何时，优先选择可验证的原生 caret 或 textarea 专用实现，不伪造浏览器 Selection。

### 2.2 本版本明确不做

- 不新增用户功能、设置、编辑器引擎、框架或数据格式。
- 不同时升级 Electron、Node、TypeScript 或其他主要依赖。
- 不试图恢复 Vditor 4.0 上游已放弃的 SV 语法高亮、自动完成或 contenteditable 行为；是否接受该上游产品变化是开始实施前的决策门。
- 不在没有差异证据时修复 [`docs/00-ISSUES.md`](00-ISSUES.md) 的 SV undo dirty-state 问题；仅把它纳入迁移验证矩阵。

## 3. 4.0 架构断点

Vditor 3.11.3 的 SV 以 `<pre contenteditable>`、嵌套 source marker、`Range`、`<wbr>` 和 `SpinVditorSVDOM()` 工作。Vditor 4.0 的 `.vditor-sv` 是 `<textarea>`：

- 输入与 undo 使用 `value`、`selectionStart`、`selectionEnd`；`Undo.renderDiff()` 不再把 patch 写回 SV `innerHTML`。
- `recordFirstPosition()` 和 undo 对 SV 不再要求 DOM `Selection`。
- `getMarkdown()` 直接读取 textarea `value`，但仍追加并规范化末尾 LF；升级不能假设应用保存基线会自动一致。
- SV 不再有可供 Desktop 读取的行 marker、padding、syntax span 或 Range 几何。

这会影响至少以下已有责任：SV 行号/空白符、自动缩进与列表缩进、source selection、查找替换、剪贴板与右键命令、divider/滚动/尾部留白、自绘 caret、SV 模式切换、undo 保存基线测试。每项必须以用户可观察行为和 Markdown 输出为验收对象，而不是保留旧 DOM 实现。

## 4. 迁移原则

1. **先决策、后安装。** 批次 0 必须确认接受 textarea SV 的上游能力变化；未确认不得修改依赖。
2. **先建立 3.11.3 基线。** 对每个受影响 SV 用户路径记录输入 Markdown、操作、预期 Markdown、selection/滚动、dirty 状态及已知限制。
3. **任何提交可构建。** 不保留同一运行路径的新旧 SV 双轨；一个语义接口迁移后在同一提交删除旧路径。
4. **以 Markdown 保真为先。** 比较保存前后和 undo/redo 后的实际字符串；视觉相同不等于文件内容相同。
5. **适配层优先但不强行适配。** 纯 Vditor 私有结构差异在 adapter 处理；textarea 使应用功能需要新的语义接口时，可重构相应 editor controller，不用伪 Range 或 DOM shim 掩盖差异。
6. **不保留无效补偿。** 如果 Vditor 4.0 已原生保证某项行为，删除 3.11.3 私有 workaround 及其过时测试，而非叠加两套恢复逻辑。

## 5. 迁移阶段

### 阶段 0：基线、产品决策与影响清单

- 冻结 0.2.5 HEAD、工作区、`package.json`/锁文件、Vditor 3.11.3 版本检查和完整测试结果。
- 在真实 3.11.3 Electron 中记录 SV 基线：编辑、撤销/重做、保存、末尾 LF/CRLF、空文档、空行、长行、列表缩进、查找替换、粘贴、右键、分栏、行号/空白符、滚动与 caret；另记录 WYSIWYG/IR 的不换行空格（U+00A0）输入/粘贴、切换模式和写盘结果。
- 明确接受 Vditor 4.0 SV textarea 及其不再支持高亮/自动完成的上游变化；若产品不接受则终止 0.2.6，不安装依赖。
- 将每个 `vditor-adapter.js` 的 SV 私有 API 分类为：可保留、textarea API 重写、移除/降级，记录到 tracker。

### 阶段 1：依赖、离线资产与最小启动

- 精确安装 `vditor@4.0.0`，更新版本检查、资产复制、类型声明、CSP/MathJax 审计和升级文档的固定版本记录。
- 验证 bundled 资源完全离线、应用能启动、Vditor 公开构造/API 契约有效、三种模式可创建和切换。
- 在此阶段不声称旧 SV 增强可用；不兼容功能应显式失败或先禁用，不能静默使用旧 DOM。

### 阶段 2：SV textarea 核心编辑与文档保真

- 将 SV 编辑根、内容读取、焦点、selection、输入、undo/redo、模式切换和保存基线调整为 textarea 语义。
- 建立保存后编辑、undo/redo 回到保存点的 dirty-state E2E；比较 `input(value)`、`savedContent`、写盘 Markdown 和首个差异 offset。
- 覆盖 LF、CRLF、无末尾换行、空文档、仅空行、中文/emoji、长行、列表、表格与 HTML 源码；WYSIWYG/IR 必须覆盖不换行空格（U+00A0）输入/粘贴、切换模式、保存重开和 dirty 基线。Vditor 4.0 会将其序列化为普通空格，必须将该上游变化作为批准的 Markdown 输出或阻塞项明确记录。
- 只有确认差异是产品允许的规范化且保存/恢复安全时，才能定义受控比较或保存规范；不得用 UI 状态、toolbar 状态或延迟自动清除 dirty。

### 阶段 3：SV 应用增强迁移

- 为 SV 定义 adapter-owned 的 offset selection 契约（`start`/`end`），替换现有 Range-only 的 capture/restore、source selection、缩进和上下文菜单状态；使用 Vditor 4.0 的 textarea/value/selection API 或等价的 textarea 操作，保持其 input 和 undo 路径。
- 重建 SV 查找替换的 offset、`selectionStart`/`selectionEnd` 和滚动行为；当前 DOM Text-node、Range 与 CSS Highlights 路径不能套用于 textarea。明确批准的视觉策略，并覆盖 selection 预填搜索、导航、单项/全部替换、undo 与保存。
- 重建或明确降级 SV 行号、空白符、滚动同步、divider、自动缩进、列表缩进、上下文菜单和剪贴板。SV 尾部留白改用 textarea `paddingBottom`，不再依赖 3.11.3 的 `--editor-bottom`/`::after`；验证不增加逻辑行号、不破坏 typewriter、滚动或分栏比例。
- 将资源健康的 SV 图片引用删除迁移到精确 textarea offset 操作，覆盖单个缺失引用、重复引用的保守拒绝、undo 和保存；不得用整篇 `getValue()`/`setValue()` 回写替代。
- 自绘 caret 在 SV 必须有 textarea 可验证的坐标策略；若无法在不引入脆弱测量的前提下实现，切换为原生 caret 并更新设置/测试契约。
- 每项迁移同时移除依赖 3.11.3 span/Range/marker 的旧代码、监听、observer、rAF 和测试，验证 tab close、rebuild、workspace 切换后无资源遗留。

### 阶段 4：三模式集成、审计与发布准备

- 回归 WYSIWYG、IR 与 SV 的内容、selection、undo/redo、工具栏、模式快捷键、预览、主题、字体、图片、表格、链接、导出和资源健康路径。
- 审查 Vditor 4.0 对 adapter 结构、CSS 覆盖、CSP、离线资产和类型 facade 的所有影响；更新 `docs/01-CODE-STRUCTURE.md`、`docs/07-VDITOR-UPGRADE.md`、README/CHANGELOG 与 tracker。
- 运行完整检查、Linux 打包和人工验收；Windows/macOS 实机验证按 [`docs/04-CROSS-PLATFORM.md`](04-CROSS-PLATFORM.md) 记录，未执行不得宣称通过。

## 6. 测试与验收

每个阶段按最小充分范围运行 `npm run format:check`、`npm run lint`、`npm run typecheck`、`npm run typecheck:renderer`、`npm run check:vditor`、`npm test`、`npm run build` 和相关 Electron E2E。阶段 4 与发布前必须运行 `npm run check:all`；打包变化还须运行适当的 Linux release 命令。

0.2.6 完成前必须满足：

- Vditor 版本、离线资产和升级文档一致固定为 `4.0.0`。
- 三种模式能编辑、保存、重开、切换和撤销/重做，且 Markdown 输出符合批准的 4.0 行为基线。
- SV 的 textarea 架构不留下对 3.11.3 marker/Range/contenteditable 的生产依赖。
- 保存点 dirty-state 矩阵可验证；[`docs/00-ISSUES.md`](00-ISSUES.md) 的问题要么有证据关闭，要么保留并明确 4.0 后的复现结果与下一步。
- 文件安全和 Electron 安全边界无回归；所有新增运行时资源有 disposer。
- 用户手测通过 Linux 矩阵，未测试平台明确记录为递延项。

## 7. 提交与文档规则

- 在 `dev-0.2.6` 或功能分支实施；一个提交只包含一个可验证迁移单元。
- 不提交 `dist/`、`static/`、release 产物或外部 `/home/shawnzhang/Projects/vditor` 的修改。
- 每个阶段结束更新 tracker 的状态、提交、验证、手测和遗留项；不把计划改写成日志。
- 只有迁移完成、文档与测试同步后才更新 `docs/01-CODE-STRUCTURE.md` 的版本/架构描述，并在发布前最后复核。
