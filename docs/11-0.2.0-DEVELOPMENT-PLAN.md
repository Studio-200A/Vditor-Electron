# Vditor-Electron 0.2.0 开发任务计划

> 项目仓库：<https://github.com/Studio-200A/Vditor-Electron>  
> 计划基线：`master` 分支，评审时 HEAD 为 `8cb3786e70dc50c84327d5510206514661534b4e`  
> 当前已发布版本：`0.1.3`
> 目标版本：`0.2.0`

> 状态说明：新版工作区 UI、查找替换、文件树基础操作和工作区内基础外部变化提示已在 0.1.3 实现；本文只把尚未完成的保存可靠性、完整 watcher 覆盖、冲突恢复和安全边界列为 0.2.0 任务。

## 1. 文档用途

本文档供 coding agent 在现有代码基础上继续开发 Vditor-Electron 0.2.0。它不是要求机械执行的静态命令清单，而是一份经过产品定位、现有架构和已知风险共同约束的开发计划。

开始编码前，agent 必须先检查当前仓库 HEAD、工作区状态、现有实现和测试结果。如果当前代码已经变化，或者某项任务的前提不再成立，应先报告差异并调整实施方案，不能为了逐字完成本文档而覆盖已有成果或引入重复实现。

## 2. 产品定位与开发边界

Vditor-Electron 的定位是一个本地优先、轻量、专注于打开和编辑普通 Markdown 文件的桌面应用。它基于 Vditor 编辑器引擎，但桌面文件生命周期、标签页、工作区、设置、主题、导出和系统集成由本项目负责。

0.2.0 必须继续遵守以下原则：

- 保持“Markdown 编辑器”定位，不扩展为知识库、数据库式笔记系统或云同步平台。
- 保持普通 `.md` / `.markdown` 文件作为真实数据源，不引入私有文档格式。
- 保持本地优先，不加入账号、遥测、在线服务或必须联网的功能。
- 保留三种 Vditor 编辑模式：所见即所得、即时渲染、分栏预览。
- 保留源码与预览的独立字体、字号、缩放和主题设置。
- 不在 0.2.0 升级 Vditor。继续固定当前 Vditor `3.11.3`，除非现有实现确实因上游缺陷无法完成任务，并在修改前说明理由。
- Vditor 私有 DOM 结构和选择器继续集中在 `src/renderer/vditor-adapter.js`，不得在其他模块随意新增散落的私有选择器。
- 不引入 React、Vue 等 UI 框架，不对渲染层进行一次性推倒重写。
- 不为了“代码看起来现代”而改变已经稳定的用户行为。

## 3. 0.2.0 版本目标

0.2.0 的显性主题是“更轻、更灵活的编辑界面”，底层目标是让应用具备更可靠的桌面文件编辑基础。

本版本应同时完成以下结果：

1. 提供完整工具栏、选区浮动工具栏、隐藏工具栏三种模式。
2. 提高文档保存、异常恢复和外部文件冲突处理的可靠性。
3. 收紧 Electron 的导航、IPC、外部链接和本地资源访问边界。
4. 修复已确认的 macOS 窗口关闭状态、目录重命名和删除后的标签页一致性问题。
5. 建立能够阻止明显回归的自动化检查和发布前验证流程。

在修改任何文件前完成以下检查，并把结果记录在开发汇报中：

# 第一部分：文档保存与异常恢复

## 5. 原子化文档保存

当前普通文档保存直接写入目标文件。0.2.0 必须改为尽可能安全的替换流程，避免程序崩溃、系统断电或磁盘错误导致原文件被截断。

要求：

- [ ] 在目标文件同目录创建唯一临时文件，避免跨文件系统移动。
- [ ] 完整写入并关闭临时文件后再替换目标文件。
- [ ] 尽可能保留原文件权限等必要元数据。
- [ ] 失败时不得提前删除或截断原文件。
- [ ] 失败后清理本次创建的临时文件；清理失败只记录相关路径，不得覆盖原始错误。
- [ ] 成功后更新 `savedContent`、修改标记、最近文件和状态提示。
- [ ] 保存失败时标签仍保持 modified 状态，并向用户显示包含文件名和可理解原因的错误。
- [ ] 自动保存与手动保存统一调用同一安全写入服务。
- [ ] 明确验证 Linux、Windows、macOS 的替换语义，不能假定三个平台的 `rename` 行为完全一致。
- [ ] 原子替换产生的 `add`、`unlink`、`rename` 或连续事件必须识别为应用自身保存，不能误报为外部冲突。

必须增加故障测试：

- 写入临时文件失败时原文件内容不变。
- 替换目标失败时原文件仍可读取，标签仍为未保存状态。
- 成功保存后临时文件不存在。
- 保存已有文件时文件权限没有无故变化。
- CRLF/LF 行尾策略继续遵守当前文档状态。

## 6. 未保存内容恢复

现有 session 主要保存工作区和已打开文件路径，不能恢复无路径的新文档和已修改但尚未写入磁盘的内容。0.2.0 增加轻量恢复机制。

要求：

- [ ] 在应用配置目录中使用独立的 recovery 数据，不把大量正文写进 `config.toml`。
- [ ] 为无路径文档和 modified 文档保存恢复快照。
- [ ] 快照至少包含稳定 ID、原文件路径（如有）、标题、正文、编码/行尾相关信息、修改时间和当前编辑模式。
- [ ] 使用防抖写入，避免每个按键都同步写磁盘。
- [ ] recovery 文件本身采用安全写入。
- [ ] 文档成功保存且内容与磁盘一致后删除对应快照。
- [ ] 用户主动“不保存”关闭文档后删除对应快照。
- [ ] 正常退出且所有文档已妥善处理后清理无用快照。
- [ ] 异常退出后再次启动，明确提示发现可恢复内容，由用户决定恢复或放弃。
- [ ] 恢复不能静默覆盖磁盘上更新的文件；如果磁盘版本已变化，应同时保留恢复内容并进入冲突状态。
- [ ] 恢复无路径文档时继续作为 Untitled 文档打开，不擅自创建磁盘文件。

验收标准：

- 新建未命名文档并输入内容，模拟异常终止后可以恢复。
- 修改已有文档但未保存，模拟异常终止后可以恢复。
- 正常保存后不再重复提示旧快照。
- 用户明确放弃恢复后，下一次启动不再提示同一快照。

# 第二部分：外部文件变化与工作区一致性

## 7. 打开文件的监控范围

当前监控主要依赖工作区 watcher，独立打开且位于工作区之外的文件也必须被监控。

当前基线：工作区 watcher 已能把 `add` / `change` 映射到已有路径标签，以及工作区根目录中 Untitled 标签的默认保存路径；应用自身保存使用短时 `ignoredChanges` 窗口抑制回调。

要求：

- [ ] 工作区内文件继续使用工作区 watcher，避免为每个文件重复监听。
- [ ] 工作区之外的已打开文件建立必要的文件或父目录监听。
- [ ] 标签关闭、文件另存、工作区切换和应用退出时正确释放监听资源。
- [ ] 同一文件被多个入口打开时不创建重复 watcher。
- [ ] 应用自身保存引发的文件变化不能被误报为外部冲突。
- [ ] 用可核验的保存操作 ID、文件版本或元数据替代固定 1.5 秒 `ignoredChanges` 时间窗，覆盖慢磁盘、网络盘、同步盘和安全软件延迟事件。
- [ ] 规范化路径身份并验证大小写敏感/不敏感文件系统、符号链接和同一文件不同路径表示的行为。
- [ ] 正确合并编辑器、资源管理器和同步软件可能产生的短时间连续 `add` / `change` / `unlink` 事件，避免重复横幅或错误自动重载。

## 8. 外部修改冲突状态

当磁盘文件变化且当前标签存在未保存内容时，不能只显示会自动消失的状态栏消息，也不能允许自动保存随后覆盖外部内容。

当前基线：冲突标签已有持续可见的 `!` 标记；活动标签在编辑区顶部显示不抢焦点的持久横幅；可选择“忽略当前标签修改并重载”或“忽略外部更改”；冲突未处理及忽略外部更改后会暂停自动保存；无本地修改的已有文件继续自动重载。sidebar 新建或重命名不会被 Untitled 标签阻止，而是由同一路径映射进入该冲突流程。

引入持久的冲突状态，例如：

```ts
type ExternalConflict = null | {
  kind: 'modified' | 'deleted';
  detectedAt: number;
  diskMtime?: number;
};
```

后续补完：

- [ ] “忽略外部更改”后的手动保存必须再次明确确认覆盖，不能仅依赖用户点击保存来推断意图。
- [ ] 外部修改补充“另存当前内容”和“明确覆盖磁盘版本”，并与现有两个横幅动作形成完整流程。
- [ ] 外部删除提供“另存当前内容”“重新创建原文件”“关闭文档”和“取消”等适当动作。
- [ ] 对删除、移动、权限变化和磁盘文件不可读分别建模，不能统一当作普通修改。
- [ ] 冲突状态保存检测时间、磁盘版本或 mtime；应用重启与 recovery 恢复后仍能识别尚未解决的冲突。
- [ ] 外部文件在横幅显示期间再次变化时更新磁盘版本，并保证“重载”读取的是用户确认时的最新稳定内容。
- [ ] 自动重载和手动重载尽可能保留或明确重置光标、选区、滚动位置、编辑模式和撤销状态。
- [ ] 多个标签映射到同一路径时只建立一个磁盘事实来源，并一致更新所有相关标签，不能产生相互覆盖。
- [ ] 解决冲突后清除标记、忽略状态和旧事件记录，并重建正确的 `savedContent` 与保存基线。

如果磁盘文件变化而标签没有本地修改，可以继续自动重新载入，但应确保光标、滚动位置和用户提示尽可能合理。

## 9. 目录重命名与删除

- [ ] 重命名目录时，更新该目录下所有已打开子文件的 `filePath`、`baseDir`、标签提示和最近文件记录。
- [ ] 更新后的相对图片资源仍能正常显示。
- [ ] 删除已打开文件时，标签进入“外部删除”状态，不能在用户不知情的情况下通过自动保存重新创建文件。
- [ ] 删除包含已打开文件的目录时，对所有受影响标签执行同样处理。
- [ ] 文件另存后重新绑定正确 watcher，并解除旧路径 watcher。
- [ ] 识别资源管理器重命名所产生的旧路径 `unlink` 与新路径 `add` 事件对，避免把应用内重命名误报为删除和外部新建两个冲突。
- [ ] 工作区切换时重新计算 Untitled 默认目标路径；旧工作区的迟到 watcher 事件不得绑定到新工作区标签。

# 第三部分：Electron 安全边界

## 10. 安全原则

Vditor-Electron 会打开用户提供的 Markdown，其中可能包含 HTML、链接和远程资源。渲染器同时能够通过 preload 调用本地文件功能，因此 0.2.0 必须缩小“渲染内容 → Electron 权限 → 本地文件系统”的组合风险。

安全加固不能只修改一个开关，必须按入口逐项检查。

## 11. 导航与外部链接

- [ ] 为 `window.open`、`will-navigate` 和 preload 暴露的 `openExternal` 使用同一套 URL 校验函数。
- [ ] 只允许明确支持的 `https:`、`http:` 和必要的 `mailto:`。
- [ ] 拒绝 `file:`、`javascript:`、`data:`、自定义应用协议和无法解析的 URL。
- [ ] 不允许 Markdown 中的链接触发应用内部导航到任意网页。
- [ ] 为 URL 校验函数增加单元测试，包括大小写、空白、编码和恶意 scheme 边界情况。

## 12. IPC 调用方校验与参数校验

- [ ] 为所有具有文件、窗口、导出、设置和外部链接权限的 IPC handler 校验 `event.senderFrame` / 来源 URL。
- [ ] 只接受来自本应用受信任 renderer 页面的调用。
- [ ] 对路径、枚举、数字范围和对象结构进行运行时校验，不能只依赖 TypeScript 类型。
- [ ] preload 不暴露底层 `ipcRenderer`，继续保持窄 API。
- [ ] 对删除、重命名、创建目录、写文件等高风险操作采用明确参数结构并返回可处理的错误。
- [ ] 把 IPC channel、输入和返回结构集中定义，避免 main、preload、renderer 三处漂移。

## 13. 本地资源协议与文件能力范围

当前本地图片协议不能继续把任意绝对路径视为可读取资源。

目标行为：

- [ ] 仅允许读取当前已打开文档、其授权资源目录或已打开工作区范围内的资源。
- [ ] 对路径进行规范化和 realpath 检查，防止 `..`、符号链接和编码绕过授权根目录。
- [ ] 不允许通过协议探测任意系统文件是否存在。
- [ ] 文档关闭或工作区关闭后撤销不再需要的访问能力。
- [ ] 继续支持 Markdown 相对图片、粘贴图片目录和现有本地预览。
- [ ] 为合法路径、越界路径、符号链接越界和不存在路径增加测试。

具体实现可以采用受控根目录集合或不可猜测的 capability token，但必须先说明选择及其生命周期。

## 14. Renderer sandbox、CSP 与 HTML 清理

- [ ] 在测试现有 Vditor、preload 和本地协议兼容性的前提下，尝试启用 BrowserWindow renderer sandbox。
- [ ] 检查 CSP 中 `'unsafe-eval'` 和 `'unsafe-inline'` 的真实依赖；能够移除的必须移除，不能移除的要在安全文档中说明具体原因和限制范围。
- [ ] 保持 `contextIsolation: true` 和 `nodeIntegration: false`。
- [ ] Markdown sanitize 默认保持开启。
- [ ] 如果继续允许用户关闭 sanitize，设置页面必须明确显示风险说明；在安全边界尚未完成前，不应让未清理 HTML 与宽泛文件能力同时存在。
- [ ] 禁止用自动添加 `--no-sandbox` 作为一般性兼容方案；如 Linux 特殊环境确实需要回退，应明确记录触发条件和风险。

如果某项因为 Vditor 或 Electron 限制无法在 0.2.0 完成，agent 必须提供复现实验、风险说明和最小替代措施，不能静默跳过。

# 第四部分：已确认缺陷修复

## 15. macOS 窗口关闭确认状态

当前关闭确认状态是进程级变量。一次确认关闭后，在 macOS `activate` 重新创建窗口时可能没有复位，从而让新窗口的未保存文档绕过确认。

要求：

- [ ] 每次创建新 BrowserWindow 时重新初始化关闭确认状态，或改为按窗口保存状态。
- [ ] 一个窗口的确认不能影响以后创建的窗口。
- [ ] 正常关闭、取消关闭、保存后关闭和“不保存”关闭均保持正确行为。
- [ ] 增加可在非 macOS 环境执行的状态单元测试；条件允许时增加 macOS 集成验证。

## 16. 设置保存不应无条件重建全部编辑器

当前保存任意设置后会重建所有 Vditor 实例，可能清除撤销栈、选区和滚动位置。

要求：

- [ ] 对设置进行分类：可热更新、只影响布局/展示、确实需要重建编辑器。
- [ ] 主题、字体、缩放、工具栏模式、侧边栏和窗口布局优先热更新。
- [ ] 只有 Vditor 初始化后无法安全改变的选项才触发重建。
- [ ] 如必须重建，尽可能保存并恢复内容、模式、光标、选区和滚动位置，并明确撤销历史限制。
- [ ] 增加测试确认只修改外观或工具栏模式后，用户仍可撤销之前的编辑。

## 17. HTML/PDF 导出中的本地图片来源

- [ ] HTML 和 PDF 导出统一使用原始 Markdown 图片来源，不输出仅在应用内部有效的 `local-file://` URL。
- [ ] 复用现有 `withOriginalImageSources` 或等价的集中能力，不创建第二套转换规则。
- [ ] 明确导出是否跟随当前内容主题；如果 0.2.0 不实现主题化导出，至少保持输出稳定并在文档中说明。
- [ ] 增加包含相对图片的导出测试，断言结果中不存在 `local-file://`。

# 第五部分：代码组织与可维护性

## 18. 渲染层修改原则

`src/renderer/app.js` 已承担标签、Vditor 生命周期、菜单、设置、工作区、主题、导出和文件状态等大量职责。0.2.0 不要求一次性重写，但新增浮动工具栏不能继续无边界地堆进同一个文件。

最低要求：

- [ ] 将工具栏模式状态、浮动工具栏生命周期、选区保存/恢复和定位计算组织为边界清晰的模块或控制器。
- [ ] 将纯状态转换和几何计算写成可单元测试的纯函数。
- [ ] Vditor DOM 查询继续通过 adapter 完成。
- [ ] 不在多个模块各自注册相互竞争的全局 `selectionchange`、`click` 和 `resize` 监听器。
- [ ] 每个标签页销毁时释放 observer、事件监听和保存的 Range 引用。

可选但非发布阻塞：逐步把 renderer 新模块写成 TypeScript，并建立共享 IPC 类型。不得以此为理由对整个 `app.js` 做高风险全量迁移。

## 19. 应用标识、依赖与构建一致性

# 第七部分：实施顺序与提交建议

## 23. 推荐阶段

### 阶段 A：基线与状态模型

1. 完成基线检查。
2. 新增 `toolbarMode` 类型、默认值、配置迁移及测试。
3. 调整菜单结构和设置 UI。
4. 暂不实现复杂浮动行为，先确保三种状态可以稳定切换和持久化。

### 阶段 C：选区浮动工具栏

1. 建立独立控制器和浮动容器。
2. 实现可编辑区域识别。
3. 实现 Range 保存、验证和恢复。
4. 实现定位、边界限制和隐藏生命周期。
5. 接入选区型 Vditor 命令。
6. 完成三种编辑模式 E2E。

### 阶段 D：保存与文件冲突

1. 原子化保存。
2. recovery 快照。
3. 工作区外文件 watcher。
4. 外部修改/删除冲突 UI。
5. 目录重命名、删除和另存后的标签及 watcher 修复。

### 阶段 E：安全加固

1. 统一 URL 校验。
2. IPC sender 和参数校验。
3. 限制本地资源协议。
4. 验证 renderer sandbox 和 CSP。
5. 调整 sanitize 风险展示。

### 阶段 F：缺陷、导出与设置热更新

1. 修复 macOS 关闭确认状态。
2. 避免设置保存无条件重建全部编辑器。
3. 修复 HTML/PDF 导出图片来源。
4. 统一应用 ID、Node 和依赖配置。

### 阶段 G：发布准备

1. 补齐单元测试和 E2E。
2. 建立 CI。
3. 执行完整检查。
4. 更新 README、升级文档、问题清单和 changelog。
5. 生成候选安装包并进行 Linux 实机冒烟测试；条件允许时验证 Windows/macOS。

## 24. 提交原则

- 每个提交只解决一个可描述的问题，避免把 UI、保存、安全和格式化混在同一提交。
- 重构提交和行为修改提交尽量分开。
- 每个阶段结束前运行与该阶段相关的测试。
- 不使用跳过测试、关闭 lint 或放宽类型来换取表面通过。
- 不批量格式化与任务无关的文件。
- 不修改 Vditor vendored 代码来绕过 adapter，除非先证明没有可维护的外部方案。
- commit message 应说明行为变化，例如：

```text
feat(toolbar): add persistent toolbar display modes
feat(toolbar): show contextual controls for editor selections
fix(files): prevent autosave from overwriting external changes
fix(save): replace documents through atomic writes
security(ipc): validate privileged renderer requests
```

# 第九部分：0.2.0 明确不做的事项

以下任务不属于 0.2.0，除非为了完成发布门槛必须做最小调整：

- Vditor 版本升级。
- React、Vue 或其他前端框架迁移。
- `app.js` 一次性全量 TypeScript 重写。
- 云同步、账号系统、协作编辑或在线存储。
- 知识库、双向链接、标签数据库、全文索引等笔记管理功能。
- 插件系统。
- 完整命令面板或复杂快捷键自定义系统。
- 把所有 Vditor 按钮都搬入浮动工具栏。
- 为没有明确需求的格式或平台增加大规模导入导出功能。
- 仅为了视觉变化重做整套主题。

这些内容如果在开发过程中被发现有价值，应记录到 `docs/00-ISSUES.md` 或 `docs/30-wishlist.md`，而不是临时扩张 0.2.0。
