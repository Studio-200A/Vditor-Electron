# Vditor-Electron 0.2.6 IPC Handler 模块化重构计划

## 1. 文档用途与状态

本文档是 0.2.6 版本内的内部重构计划：把 `src/main/index.ts` 中 `registerIpcHandlers()` 集中注册的全部 64 个 IPC handler 按领域拆分为职责明确的模块。按顺序执行两个独立 goal：Goal 1 完成阶段 0–2，Goal 2 在 Goal 1 完成后执行阶段 3–5。每个 goal 可跨多次接续执行，但必须完成其包含的全部阶段、专项验证和交接总结后才结束。不另建执行 tracker；阶段勾选与验证记录留在本文档，长期风险的状态只在 `docs/00-ISSUES.md` 更新。0.2.6 发布归档时将本文档移入 `ARCHIVED/`。

这是一次**行为保持型重构**：通道名、请求/返回形状、错误语义、preload 桥接和渲染器消费方式全部不变。对应 `docs/00-ISSUES.md` 架构风险点 #2 与 P2 改进建议 #3，并顺带以通道覆盖测试部分缓解风险点 #3。

## 2. 现状与动机

- `src/main/index.ts` 共 942 行，混合四类职责：应用启动/生命周期、窗口状态持久化、菜单/本地化、IPC handler 注册（约 460 行）。
- `registerIpcHandlers()` 注册 56 个 `handleTrusted`（invoke）与 8 个 `onTrusted`（send）handler，覆盖 `IPC_CHANNELS` 中全部 64 个渲染器→主进程通道（其余 7 个为 main→renderer 事件通道）。
- 信任校验（`requireTrustedMainFrame`）与参数解析（`ipc-validation.ts`）已模块化，但 handler 实现体全部内联在 `index.ts`，新增/修改任何通道都要触碰应用入口文件。
- handler 与模块级可变状态（`mainWindow`、`rendererReady`、`pendingOpenFiles`、`resourceHealthMenuEligible`、`exportWebContents`）交织，职责边界不清晰。

## 3. 范围与非目标

### 3.1 本计划必须完成

- 建立 `src/main/ipc/`：1 个信任包装模块、11 个领域注册模块和 1 个可单独导入的总注册模块（见 §4）。把 64 个 handler 全部迁入领域模块。
- `registerIpcHandlers()` 收口为可单独导入的组合函数：由 `index.ts` 注入已初始化服务与窄回调，总注册模块创建信任包装器并调用 11 个领域注册函数。
- `index.ts` 中的 handler 实现体、`handleTrusted`/`onTrusted`/`reportIpcFailure` 包装器、`chooseSavePath`、`readClipboardContents` 全部移出。

### 3.2 明确不做

- 不拆 `index.ts` 的窗口状态持久化、open-file 队列、菜单/本地化、单实例逻辑（`tr()`/`getEffectiveLocale`/`updateApplicationMenu` 等保留在 `index.ts`，经依赖注入或回调供 IPC 模块使用；属后续迭代的架构演进）。
- 不改 `src/main/ipc-contract.ts` 的通道名与形状，不改 `src/main/preload.ts`，不改渲染器调用方式（preload 与 renderer 在整个重构中保持零 diff）。
- 不新增 handler 能力：`00-ISSUES.md` P1 建议（`file:write`/`file:delete` 路径授权校验、`app:openExternal` URL 长度上限）是独立改进，不并入本次重构。
- 不引入事件总线、全局单例或新的通用 IPC 包装层。

## 4. 目标结构

### 4.1 设计规则

1. **懒窗口引用**：handler 注册发生在 `createWindow()` 之前，所有涉及 `mainWindow` 的依赖一律以 `getMainWindow: () => BrowserWindow | null` 注入；调用时再读取。`file-dialogs` 等原有 `mainWindow!` 非空断言语义原样保留，不把注册时的 `null` 缓存下来。
2. **共享可变状态所有权不动**：`rendererReady`/`pendingOpenFiles`、`resourceHealthMenuEligible`、窗口最大化状态机、`windowCloseConfirmation` 仍由 `index.ts` 持有，IPC 模块只经窄回调（`onRendererReady`、`onMenuEligibilityChanged` 等）触发，不复制状态。
3. **回调命名用例**：注入回调命名其效果（`onRendererReady`、`onMenuAffectingSettingsChanged`），不引入通用 `handle`/`data`。
4. **行为保持**：每个 handler 的信任校验、参数校验顺序、错误路径、返回值、同步/异步行为和副作用时机按当前源码逐项迁移，不“顺手”修正既有行为。当前 invoke 的 `requireTrustedMainFrame()` 在 `try` 外，拒绝时直接抛 `IpcRequestError('IPC_UNTRUSTED_RENDERER')`；send 的校验在 `try` 内，拒绝时经 `reportIpcFailure()` 处理。这一差别必须保留。
5. **共享对话框能力**：`chooseSavePath` 接收懒窗口 getter 或由已注入 getter 创建；`export-pdf.ts` 可以复用它，但不得通过模块级可变窗口引用、循环导入或另一个领域注册函数获取对话框能力。
6. **禁止双轨**：一个领域模块迁移完成并通过验证后，同一变更内删除 `index.ts` 对应旧实现；不保留新旧两份等待统一删除。
7. **strict TypeScript**：各 `<X>Deps` 用显式 interface 定义，服务类型直接引用已有类；禁 `any` 与 lint 抑制。
8. **工作区与提交**：迁移前查看已有改动；只修改本计划范围内的文件，不覆盖用户工作。每个有代码或文档改动的阶段完成专项验证后单独选择性暂存并提交，使用英文 Conventional Commit；不把已有无关改动并入提交。阶段内若有多个独立模块，可按需增加更小的提交，但不得把两个阶段合为一个提交。阶段 0 若仅核对基线而没有文件变化，不创建空提交。

## 5. 迁移阶段与验收标准

Goal 1 执行阶段 0→1→2；完成阶段 2 后总结已提交的变更、专项测试、未验证边界，并提示用户手动运行全量测试。Goal 2 在 Goal 1 的提交与交接记录可核对后执行阶段 3→4→5；用户若已提供 Goal 1 全量测试结果，先处理其中与本重构有关的失败。Goal 2 完成后同样总结并提示用户手动运行全量测试。用户尚未提供全量结果，不视为通过，也不妨碍继续完成本计划中可独立验证的下一阶段。

每完成一个阶段，简要记录所做工作、实际运行的专项命令及结果、尚未解决的失败和下一阶段入口；提交可通过 Git 历史核对，无须在文档中逐项填写哈希。goal 结束总结列出阶段提交信息即可，必要时附哈希。接续执行时从最后一个有证据的阶段继续。阶段边界可以根据实际依赖调整测试或增加中间提交，但不能漏掉 64 个通道的迁移、两类注册方向的覆盖和最终文档收口。若专项 E2E 在断言前因环境无法启动，记录环境限制并继续完成不依赖该环境的工作；不得写成测试通过或用单测代替。

交给执行 agent 的两个目标依次为：

1. **Goal 1**：完成本计划阶段 0–2；每阶段单独提交英文 Conventional Commit，按需增减并运行专项测试；结束时列出提交、验证、遗留边界，提示用户手动运行全量 `npm run check:all`。
2. **Goal 2**：在 Goal 1 交接可核对后完成阶段 3–5；沿用同样的阶段提交与专项测试规则；结束时列出提交、验证、遗留边界，提示用户手动运行全量 `npm run check:all`。用户提供 Goal 1 的全量失败结果时，先修复本重构造成的回归。

## 8. 验证命令

agent 在 Goal 1 和 Goal 2 中均不运行全量 `npm test`、全量 `npm run test:e2e`、`npm run check` 或 `npm run check:all`。每个 goal 完成后提示用户手动运行 `npm run check:all`；该命令包含格式、项目检查、lint、两侧类型检查、Vditor 检查、单测、构建和全量 E2E，用户运行前也应按仓库规则清除生成输出。用户未反馈结果时仅报告专项证据和全量门禁待完成；Linux 专项通过也不推断 Windows/macOS 实机行为。
