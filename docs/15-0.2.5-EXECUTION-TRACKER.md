## 1. 这份文档如何使用

本文件不是第二份重构计划，也不是要求 Agent 机械执行的函数级任务清单。三类信息应保持分离：

| 信息                                 | 作用                                                   | 更新频率                  |
| ------------------------------------ | ------------------------------------------------------ | ------------------------- |
| `14-0.2.5-RENDERER-REFACTOR-PLAN.md` | 定义 0.2.5 重构的目标架构、原则、阶段和完成标准        | 目标确实改变时才更新      |
| 本文件                               | 记录施工批次、依赖、实际进度、提交、验证结果和遗留问题 | 每个批次结束时更新        |
| 当前 Session 施工方案                | Agent 根据当前代码在内部维护本轮步骤，不另建长期文档   | 每个开发 Session 临时生成 |

默认采用自主执行模式。用户在新 Session 中只需指定批次编号，Agent 负责：

1. 按第 2.1 节定向阅读和检查基线，不通读所有文档与源码。
2. 根据当前代码自行规划并直接实施，不等待用户例行批准。
3. 自行完成实现、普通错误排查、自动化测试、Tracker 更新和提交。
4. 只有遇到产品行为选择、范围扩大、现有修改冲突或无法继续时，才使用交互式问答询问用户。
5. 完成后按第 8 节汇报，并提供普通用户可执行的手测步骤。
6. 用户手测失败时留在当前 Session 修复；通过后结束，不自动进入下一批次。
7. 审查批次和决策批次（zustand 评估）按其施工卡先报告发现或结论，不自行修改；仅当用户批准引入 zustand 后，替换实施才属于该批次范围。

批次状态主值只使用以下值：`未开始`、`规划中`、`实施中`、`待手测`、`已完成`、`阻塞`。只有代码、要求的自动化检查和约定的手测均完成后，才能把对应批次标记为 `已完成`。

### 1.1 批次合并原则

0.2.0 tracker 的教训是批次拆得过碎（23 个批次/子批次），跨 Session 的依赖和记录成本偏高。0.2.5 按重构计划的模块域合并为 12 个批次，并遵守以下约定，保证合并不降低质量：

- 一个批次对应一个可独立验收的模块域（构建基础、基础 UI、状态模型、文档、编辑器、工作区/设置/导出等），批次内部允许较大工作量。
- 批次内部按施工卡列出的有序子步骤推进；每个子步骤完成后立即运行该步骤要求的验证，不把风险累计到批次末尾。
- 每个提交仍只迁移一个可独立验证的职责单元，保持可构建、可回滚；批次大不等于提交大。
- 计划第 4、22-25 节的质量约束（行为保持、测试迁移、泄漏检查、fake 接口）在每个迁移批次内同步执行，不单列批次。
- 高风险阶段保留独立复核批次（批次 7）和最终审查批次（批次 11），不因合并取消。
- 批次 6 的 zustand 引入评估是用户要求增设的决策批次，结论必须由用户确认后才能进入后续施工。

## 2. 使用原则

- 每个 Session 默认只处理一个批次。Agent 发现相邻问题时先记录，不自行扩大范围。
- 开工前必须重新检查 HEAD、工作区和实际代码。本文件中的基线结论可能随提交变化。
- 用户已有修改必须保留。若改动直接冲突，Agent 应停下来说明；无关改动不得回退或混入提交。
- 不预先锁定 bundler 选型、文件名、函数名或实现技巧。施工方案必须来自当时的代码；重构计划中的目录结构是建议而非模板。
- 行为保持优先：除计划第 28 节明确允许的细小修复外，不得借重构改变用户可观察行为；发现缺陷先加复现测试，再决定纳入或记录到 `docs/00-ISSUES.md`。
- 渐进迁移：任何提交之后应用都必须能构建并正常启动；一个职责域完成接入并通过验证后，必须在同一迁移中删除旧实现，不保留新旧双轨。
- 每个迁移批次必须先按计划第 4.6 节排查多重写入者、重复监听、延迟补偿和 fallback 叠加，再开始搬迁。
- 普通实现错误和测试失败由 Agent 自行排查。只有产品行为需要选择、范围必须扩大、现有修改会被覆盖或确实无法继续时才询问用户。
- 自动化测试验证内部机制和失败场景；用户手测只验证能观察到的行为，重点是“与 0.2.0 相比行为是否悄悄变化”。
- 未实际运行的检查不得写成“通过”。E2E 若因 Electron/Chromium 启动环境受限而未运行，应明确记为环境限制。
- 对资源受限的本地全量 E2E，首轮单项断言失败而连续精确重跑通过时，记录为“待确认的不稳定结果”，不得记作干净全量通过；在相同代码上取得一次完整 `check:all` 通过后才可关闭批次门禁。
- 不因 Linux 测试通过而声称 Windows 或 macOS 已验证；跨平台边界遵循 [`docs/03-CROSS-PLATFORM.md`](03-CROSS-PLATFORM.md)，重构不得把 Linux 假设固化进 renderer。
- 0.2.5 整个版本的开发、测试与打包只在 Linux 平台完成，本版本没有 Windows/macOS 测试机与打包环境。需要实体机验证的行为一律记录为递延项，不阻塞 0.2.5 发布验收；可自动化模拟的平台差异继续通过 fake bridge 输入覆盖。
- Vditor 保持 `3.11.3`，不修改 vendored 文件。Vditor 私有 DOM 操作继续集中在 `src/renderer/vditor-adapter.js`。
- 保持 `contextIsolation: true` 和 `nodeIntegration: false`；preload 只增窄接口，不加通用 IPC 包装。
- 文件安全契约（身份、保存基线、冲突、不可用、恢复、watcher、TOCTOU 边界）以 [`docs/05-FILE-SAFETY.md`](05-FILE-SAFETY.md) 为准，重构只允许搬迁结构，不允许改变语义。

## 4. 验证命令

按修改范围选择最小充分检查，批次结束前再执行约定的完整检查。

| 命令                         | 用途                                         |
| ---------------------------- | -------------------------------------------- |
| `npm run format:check`       | Prettier 检查                                |
| `npm run lint`               | ESLint 检查                                  |
| `npm run typecheck`          | main/preload TypeScript 类型检查             |
| `npm run typecheck:renderer` | renderer TypeScript 类型检查（strict）       |
| `npm run check:vditor`       | 确认 Vditor 固定版本与离线资产约束           |
| `npm test`                   | Vitest 单元/集成测试                         |
| `npm run build`              | 编译 main + renderer 并复制静态资源          |
| `npm run build:renderer`     | 使用 esbuild 打包 renderer TypeScript 入口   |
| `npm run test:e2e`           | 构建并运行 Electron Playwright E2E           |
| `npm run check`              | 除 E2E 外的完整检查（含 typecheck:renderer） |
| `npm run check:all`          | `npm run check` 加 Electron E2E              |

规则：

- 所有迁移批次都触碰 renderer，收口前原则上运行 `npm run check:all`。
- 批次 1 会新增 `build:renderer` 与 `typecheck:renderer`（命名以实际实现为准）并纳入 `check`；完成后由批次 1 更新本节命令表。
- 发布打包不包含在日常 `check:all` 中。只在批次 10 运行对应 `npm run release:linux:*`，并执行真实安装包冒烟测试。

WorkspaceController（根路径、watcher 事件、刷新请求）与 ExplorerController（文件树 UI、展开状态、右键菜单、目录命令）。工作区、文件和目录重命名/删除引起的打开文档绑定变化，必须调用 `DocumentController` 在本批次新增的命名 binding-transition 命令；WorkspaceController/ExplorerController 不得直接修改 document、fileIdentity、保存基线、冲突或不可用状态，也不得接管主进程的 document watcher generation/revision 所有权。
2. SettingsController、SettingsWindow 与 LocalizationController：草稿、验证、保存、重置、分类；纯函数 `classifySettingsChange(previous, next)` 把设置差异分类为明确运行时影响，展示类设置不得触发无关 Vditor 重建；ThemeController/PresentationController 提供热应用接口；LocalizationController 负责 locale resolution、应用级 DOM 文案、NotificationsController locale、菜单刷新和自身 cleanup。主题样式只经状态与语义接口应用，不字符串拼接注入样式。
3. 持久化按语义拆分：各平台既有配置目录（由 `src/main/app-paths.ts` 解析，Linux、Windows、macOS 一致）中的 `config.toml` 仅保留用户偏好；同目录新增版本化 `state.json`，承载需要跨启动保留的应用状态：recent 文件/目录、session 打开标签和活动标签、workspace/每工作区展开状态、确认过的对话框目录以及窗口/UI 恢复状态。两者均是受支持、需可靠保存的持久化数据，只是 schema、生命周期与重置边界不同。主进程以白名单 schema、原子且串行的写入与窄 IPC 提供 state 能力；损坏或未知版本 state 安全降级并报告诊断，不阻止启动。首次升级从旧 TOML 读取状态字段并幂等迁移，已有有效 state 不被覆盖，之后不再把状态字段写回 TOML。recovery 快照与任何 runtime handle 不进入 `state.json`。
4. MenuController 与 WindowController：菜单根据 store 状态生成勾选项并调用公开命令，不直接跨模块改 store；窗口级显示状态和非编辑器 context menu 由明确 controller 管理。
5. ExportController：通过文档/编辑器控制器获取内容，图片来源修复、主题策略和写文件由明确依赖完成。
6. 替换本域相关的源码字符串测试；覆盖 `en_US`、`zh_Hans`、`zh_Hant` 的 locale 热切换，确认菜单、dialog、empty state 与 notifications 不遗留旧语言。

**不包含范围：** 不重做设置页、文件树或菜单视觉；不改变导出格式；不重写批次 5 的 EditorController 或批次 4 的文件安全语义。

**必须证明：** 展示类设置热应用不重建编辑器、不清空撤销历史；确需重建的选项清单与 0.2.0 一致并有证据；三种支持 locale 的热切换同步更新所有应用级文案；多次打开/关闭设置窗口不累积 listener；切换工作区不保留旧 watcher 订阅；导出 HTML/PDF 不含 `local-file:`/`app://`；PDF 隐藏窗口隔离不回归。Linux、Windows、macOS 路径测试均证明 `config.toml` 与同目录 `state.json` 的位置正确；旧 TOML 状态只迁移一次，已有 state 不被覆盖，损坏/未知版本 state 安全降级；设置重置不清除 state，清除 state 不改变用户偏好。

**用户手测重点：** 修改主题、字体、缩放、工具栏和布局设置后撤销历史仍在；工作区树操作、目录重命名/删除、HTML/PDF 导出与 0.2.0 对比。

- 新增 `DocumentSaveController` 与 `DocumentCloseController`，并由 `DocumentController` 组合持有；`saveTab()`、`closeTab()` 现在经 DocumentController 的命令入口进入。保存按 document ID 和 canonical identity 串行化，前次失败不会阻塞后续保存，完成的 operation handle 会从控制器移除；关闭固定为“确认（含必要的保存）→ 过渡期编辑器 runtime 释放与 recovery 清理 → Store 删除 → watcher/resource/UI 收敛”。关闭确认取消时不会触发任何释放或 Store 删除。

- 写入成功后在读取目标目录等后续异步步骤完成时再次确认同一 Store/binding，避免安全写入已经成功但迟到的元数据提交重建已关闭或另存后的 tab 绑定。
