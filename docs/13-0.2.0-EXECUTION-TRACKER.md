## 1. 这份文档如何使用

本文件不是第二份开发计划，也不是要求 Agent 机械执行的函数级任务清单。三类信息应保持分离：

| 信息                           | 作用                                                   | 更新频率                  |
| ------------------------------ | ------------------------------------------------------ | ------------------------- |
| `12-0.2.0-DEVELOPMENT-PLAN.md` | 定义 0.2.0 最终应达到的产品、安全和质量目标            | 目标确实改变时才更新      |
| 本文件                         | 记录施工批次、依赖、实际进度、提交、验证结果和遗留问题 | 每个批次结束时更新        |
| 当前 Session 施工方案          | Agent 根据当前代码在内部维护本轮步骤，不另建长期文档   | 每个开发 Session 临时生成 |

默认采用自主执行模式。用户在新 Session 中只需指定批次编号，Agent 负责：

1. 按第 2.1 节定向阅读和检查基线，不通读所有文档与源码。
2. 根据当前代码自行规划并直接实施，不等待用户例行批准。
3. 自行完成实现、普通错误排查、自动化测试、Tracker 更新和提交。
4. 只有遇到产品行为选择、范围扩大、现有修改冲突或无法继续时，才使用交互式问答询问用户。
5. 完成后按第 8 节汇报，并提供普通用户可执行的手测步骤。
6. 用户手测失败时留在当前 Session 修复；通过后结束，不自动进入下一批次。
7. 审查批次按其施工卡先报告发现，不自行修改。

批次状态主值只使用以下值：`未开始`、`规划中`、`实施中`、`待手测`、`已完成`、`阻塞`。如果本地闭环与跨平台实体机证据由不同文档分别管理，状态栏可以补充“本地闭环完成；跨平台验证已移交”等范围说明；只有代码、要求的自动化检查和约定的手测均完成后，才能把对应范围标记为 `已完成`。

## 2. 使用原则

- 每个 Session 默认只处理一个批次。Agent 发现相邻问题时先记录，不自行扩大范围。
- 开工前必须重新检查 HEAD、工作区和实际代码。本文件中的源码行号和基线结论可能随提交变化。
- 用户已有修改必须保留。若改动直接冲突，Agent 应停下来说明；无关改动不得回退或混入提交。
- 不预先锁定未来的函数名、文件名、延迟时间或实现技巧。施工方案必须来自当时的代码。
- 普通实现错误和测试失败由 Agent 自行排查。只有产品行为需要选择、范围必须扩大、现有修改会被覆盖或确实无法继续时才询问用户。
- 自动化测试验证内部机制和失败场景；用户手测只验证能观察到的行为，不要求用户检查源码。
- 一个提交只解决一个可清楚描述的问题。是否需要多个提交由本批次施工方案决定。
- 未实际运行的检查不得写成“通过”。E2E 若因 Electron/Chromium 启动环境受限而未运行，应明确记为环境限制。
- 不因 Linux 测试通过而声称 Windows 或 macOS 已验证；跨平台逻辑的可模拟范围和实机验证矩阵见 [`docs/03-CROSS-PLATFORM.md`](03-CROSS-PLATFORM.md)。
- Vditor 保持 `3.11.3`。Vditor 私有 DOM 操作继续集中在 `src/renderer/vditor-adapter.js`。
- 保持 `contextIsolation: true` 和 `nodeIntegration: false`，不以 `--no-sandbox` 作为一般兼容方案。
- 本版本只完善本地 Markdown 文件编辑、桌面集成和安全边界，不扩展产品形态或数据模型。

## 4. 验证命令

| 命令                   | 用途                                  |
| ---------------------- | ------------------------------------- |
| `npm run format:check` | Prettier 检查                         |
| `npm run lint`         | ESLint 检查                           |
| `npm run typecheck`    | main/preload TypeScript 类型检查      |
| `npm run check:vditor` | 确认 Vditor 固定版本与离线资产约束    |
| `npm test`             | Vitest 单元测试                       |
| `npm run build`        | 编译 main 并复制 renderer/Vditor 资产 |

| `npm run check`        | 除 E2E 外的完整检查                   |
| `npm run check:all`    | `npm run check` 加 Electron E2E       |

规则：

- 同时影响 main/preload/renderer 或 renderer shell 的功能批次，完成前原则上运行 `npm run check:all`。
- 只改纯函数或文档时可以先运行针对性测试和 `npm run check`，但必须在阶段审查或发布准备时补齐 E2E。

### ✅  批次 1：安全文档保存

**解决的问题：** 写入中断或替换失败不能截断原文件；手动保存和自动保存使用同一可靠写入路径，并为 watcher 留下可直接比较的预期正文。

**包含范围：** 单一安全写入服务、可注入文件系统操作、同目录唯一临时文件、完整写入与同步、关闭和替换、必要元数据、跨平台替换结果模型、失败清理、可理解错误、现有编码和行尾策略、无变化跳过落盘及保存成功后的预期正文更新。优先使用经过验证的原子写入库。

**不包含范围：** recovery、完整 watcher 重构、外部冲突新动作。

**必须证明：** 正常保存；临时写入失败原文件不变；替换失败原文件可读且标签仍未保存；成功无临时文件；权限不无故变化；CRLF/LF 不回归；自动保存经过同一服务；内容未变化时不替换文件或改变 mtime；保存后预期正文与实际磁盘正文一致。

**用户手测重点：** 普通保存、另存为、自动保存和一个由 Agent 提供的安全失败模拟。破坏性磁盘故障不要求用户手工制造。

**完成标准：** 针对性故障测试和 `check:all` 通过，或如实记录 E2E 环境限制；Tracker 记录最终替换语义、持久性边界、预期正文更新时机和跨平台未验证项，供批次 3 直接消费。

**必须证明：** 非可信来源和子 frame 的特权调用被拒绝；来源校验不使用字符串前缀或模糊 host 匹配；畸形或超限参数在文件系统、对话框或 shell 副作用前被拒绝；合法调用保持兼容；preload 仍为窄 API；renderer 错误不泄露内部堆栈；高风险文件操作返回可处理的领域错误。

**用户手测重点：** 正常打开、保存、重命名、删除、设置、导出和窗口控制。恶意输入由测试完成。

**完成标准：** IPC 边界测试和 `check:all` 通过；Tracker 记录主 frame helper、已覆盖的高风险 handler、validator 和错误契约；集中通道/类型定义时避免无关的大规模迁移。

### ✅  批次 9.1：长表格单元格编辑横向滚动专项

**启动条件：** 批次 9 已完成用户手测、约定的最终全量检查并完成本次 Tracker 收口；本批次已在其后启动并完成代码与专项手测，尚不与批次 10 并行实施。

**问题来源：** 2026-08-28 P09 手测反馈中的额外问题。最初表现为 Rime 中文上屏后表格回到最左侧；后续通过多字符中英文粘贴确认，根因是 Vditor 重建表格时丢失横向滚动状态，而不是 IME 专有问题。

**当前实现线索：**

- 项目固定使用 Vditor `3.11.3`；其表格样式使用 `display: block`、`overflow: auto` 和单元格 `white-space: nowrap`，长内容的横向位置由表格滚动容器持有。
- Vditor 在 `compositionstart`/`compositionend` 期间维护输入法锁；非 Firefox 路径在 `compositionend` 后重新处理当前编辑块，并通过 `SpinVditorDOM` 重建内容、再恢复光标。若当前块涉及表格，需重点验证重建是否替换了表格节点并丢失 `scrollLeft`。
- Desktop 的 `onEditorInput` 当前只更新标签正文、恢复快照、修改状态和相关 UI，没有直接调用 `setValue()` 或主动设置编辑器选区；暂未发现应用层普通输入监听器会直接把表格滚动到左侧。
- Desktop 对 `.editor-host` 和 `.vditor-content` 使用 `overflow: hidden`，并对编辑区设置宽度、内边距和 `scrollbar-gutter`；这些布局约束可能改变 Vditor 表格实际滚动容器或重排后的滚动恢复行为。
- 官方指南保存页加载的 Vditor JS/CSS 与本项目固定的 `3.11.3` 二进制一致；其公开初始化选项的本地近似配置仍复现，`typewriterMode` 已排除为主要变量。

**待验证假设：**

1. **已确认：** Vditor 重建当前表格或父级块，新表格默认 `scrollLeft = 0`；多字符粘贴与多字 IME 提交均可触发。
2. **已确认：** 该基础行为可在纯 Chromium Vditor `3.11.3` 对照页复现，不是 Desktop 壳层独有。
3. **Desktop 策略：** 重建前快照、重建后恢复表格横向位置；光标越出可视区域时以最小距离使其可见。

**实施范围：**

- [x] 建立 Chromium Vditor `3.11.3` 对照页并比较官方保存页资产、公开选项与 Desktop。
- [x] 确认实际滚动容器是表格本身，重建会丢失 `scrollLeft`；覆盖 IR、WYSIWYG、中英文单字符/多字符输入、Rime 与粘贴手测。
- [x] 在 adapter 内实现输入、粘贴、composition 前快照和有界重建后恢复；不改写 Vditor 文本、选区或 undo 路径。
- [x] 让表格滚动条遵循应用的 `always`、`auto`、`hidden` 设置。
- [x] 补齐以真实 ClipboardEvent/Vditor paste handler、右边界锚定和中间位置光标可见性为准的 Electron 回归测试。

**不包含范围：** Vditor 升级、Rime 配置重做、全部 renderer 重构，以及与本问题无关的表格功能或导出功能改造。批次 9.1 的专项验证不替代批次 9 的最终全量检查。

**完成标准：** 能用证据说明责任边界；在约定支持的编辑模式和输入路径下，长内容单元格中文输入、拼音提交和标点输入不会把横向视图无故带回最左侧，光标保持可见；英文、粘贴、撤销、保存和表格既有操作不回归；若确认是上游或环境限制而无法在本项目修复，必须留下可复现条件、影响范围和明确的残余风险记录。

**问题清单（按严重程度）：**

以下 1–10 项保留初始只读复核时的症结、当时源码定位和未覆盖场景，作为批次 7 的发现历史；当前关闭状态以其后的“修复 TODO”“本地验证”和“当前未覆盖场景”为准，不能仅按发现时的行号判断现状。

1. **高：保存期间继续编辑会被旧保存结果错误标记为已保存。** [app.js](../src/renderer/app.js#L1868) 在 `writeDocument()` 完成后无条件写回捕获时的 `content`，清除 `modified` 并删除 recovery。若保存 A 期间用户输入 B，B 可能仍显示在 Vditor 中，但标签已不脏、关闭时不再确认，且 recovery 已被清理。并发手动保存和自动保存还可能后完成的旧操作覆盖较新的磁盘正文。

2. **高：文件重命名缺少目标冲突保护。** [file-manager.ts](../src/main/services/file-manager.ts#L168) 直接调用 `fs.promises.rename()`，没有检查目标是否已存在。Linux/POSIX 下重命名到已有文件可能替换目标文件；当前测试只覆盖目标不存在的正常路径。大小写仅变化的重命名也没有独立结果模型。

3. **高：Save As 可以写入另一个已打开标签的路径并形成重复路径映射。** [app.js](../src/renderer/app.js#L1875) 没有检查目标是否已被其他标签占用。成功后两个标签共享一个 `filePath`，且目标标签的未保存内容可能被覆盖，破坏“一个文件一个标签状态”的前提。

4. **高：同一 watcher binding 内没有异步读取顺序保护。** [file-watch-service.ts](../src/main/services/file-watch-service.ts#L198) 只检查 binding generation；连续事件启动的两个读取共享同一 generation，旧读取可以晚于新读取完成并发送旧正文，污染 renderer 的冲突或自动重载状态。现有测试只验证 cleanup 后的迟到读取，没有验证同一 binding 内的乱序结果。

5. **高：watcher 重绑使用 `ignoreInitial`，没有确认重绑后的当前磁盘事实。** [app.js](../src/renderer/app.js#L371) 重新绑定后只注册 watcher。外部修改若发生在 suspend/rebind 空窗内，重新绑定时不会产生初始事件，可能被永久漏报。该风险存在于目录重命名、Save As 失败恢复、打开文件的 read/watch 间隙以及 watcher 切换场景。

6. **高：renderer 和主进程的文件身份规则不一致。** renderer [normalizedFilePath()](../src/renderer/app.js#L333) 在所有平台转小写；主进程 [normalizePath()](../src/main/services/file-watch-service.ts#L290) 仅 Windows 转小写并使用 `realpath`。Linux 大小写不同的两个文件会被错误合并；符号链接和真实路径可能形成两个标签但只有一个 watcher，关闭别名还可能解除仍在使用的 watcher。

7. **中高：外部变化检查和最终安全替换之间存在 TOCTOU 覆盖窗口。** renderer 先读取并比较基线，再调用没有携带基线的 [file:writeDocument](../src/main/index.ts#L342)。外部程序若在检查通过后、rename 前修改文件，SafeFileWriter 仍会替换它；自身写入标记和 watcher 合并还可能掩盖该变化。长期契约与关闭条件见 [`docs/05-FILE-SAFETY.md` §7](05-FILE-SAFETY.md#7-已知原子性边界已有目标的-toctou)。

8. **中高：session 恢复和 recovery 恢复可能为同一路径创建两个标签。** [restoreRecoverySnapshots()](../src/renderer/app.js#L2096) 在 session 标签恢复之后直接创建 `unchanged` recovery 标签；现有 recovery E2E 关闭了 `restoreTabs`，没有覆盖真实组合。另有 [RecoveryStore.diskState()](../src/main/services/recovery-store.ts#L139) 直接按 UTF-8 原文比较，无法正确处理 CRLF、UTF-8 BOM 和 GB18030，可能把未变化磁盘误判为 changed。

9. **中：工作区切换和目录重命名缺少完整的 transition/revision 与事务收敛。** [setWorkspace()](../src/main/services/file-watch-service.ts#L52) 在等待旧 watcher 关闭期间没有失效旧请求；并发调用可能最终让主进程监听旧工作区。目录重命名在文件系统成功后逐个更新标签和设置，任一中间 await 失败都可能留下部分新路径、部分旧路径和不完整 watcher 绑定。

10. **中：Vditor 尚未 ready 时保存入口仍可用。** [updateActiveUI()](../src/renderer/app.js#L2157) 对已有标签直接启用保存，[currentContent()](../src/renderer/app.js#L1853) 只要实例存在就调用 `getValue()`，没有保证初始化阶段返回完整正文。启动文件尚未完成 `after()` 时触发保存的场景未覆盖。
