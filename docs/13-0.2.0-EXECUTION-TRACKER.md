## 1. 这份文档如何使用

本文件不是第二份开发计划，也不是要求 Agent 机械执行的函数级任务清单。三类信息应保持分离：

| 信息                           | 作用                                                   | 更新频率                  |
| ------------------------------ | ------------------------------------------------------ | ------------------------- |
| `12-0.2.0-DEVELOPMENT-PLAN.md` | 定义 0.2.0 最终应达到的产品、安全和质量目标            | 目标确实改变时才更新      |
| 本文件                         | 记录施工批次、依赖、实际进度、提交、验证结果和遗留问题 | 每个批次结束时更新        |
| 当前 Session 施工方案          | Agent 根据当前代码在内部维护本轮步骤，不另建长期文档   | 每个开发 Session 临时生成 |

默认采用自主执行模式。用户在新 Session 中只需指定批次编号，Agent 负责：

1. 按第 2.1 节定向阅读和检查基线，不通读所有文档与源码。
2. 根据当前代码自行规划并直接实施，不等待用户例行批准。
3. 自行完成实现、普通错误排查、自动化测试、Tracker 更新和提交。
4. 只有遇到产品行为选择、范围扩大、现有修改冲突或无法继续时，才使用交互式问答询问用户。
5. 完成后按第 8 节汇报，并提供普通用户可执行的手测步骤。
6. 用户手测失败时留在当前 Session 修复；通过后结束，不自动进入下一批次。
7. 审查批次按其施工卡先报告发现，不自行修改。

状态只使用以下值：`未开始`、`规划中`、`实施中`、`待手测`、`已完成`、`阻塞`。只有代码、要求的自动化检查和约定的手测均完成后，才能标记为 `已完成`。

## 2. 使用原则

- 每个 Session 默认只处理一个批次。Agent 发现相邻问题时先记录，不自行扩大范围。
- 开工前必须重新检查 HEAD、工作区和实际代码。本文件中的源码行号和基线结论可能随提交变化。
- 用户已有修改必须保留。若改动直接冲突，Agent 应停下来说明；无关改动不得回退或混入提交。
- 不预先锁定未来的函数名、文件名、延迟时间或实现技巧。施工方案必须来自当时的代码。
- 普通实现错误和测试失败由 Agent 自行排查。只有产品行为需要选择、范围必须扩大、现有修改会被覆盖或确实无法继续时才询问用户。
- 自动化测试验证内部机制和失败场景；用户手测只验证能观察到的行为，不要求用户检查源码。
- 一个提交只解决一个可清楚描述的问题。是否需要多个提交由本批次施工方案决定。
- 未实际运行的检查不得写成“通过”。E2E 若因 Electron/Chromium 启动环境受限而未运行，应明确记为环境限制。
- 不因 Linux 测试通过而声称 Windows 或 macOS 已验证。跨平台逻辑可由 Linux 上的纯测试覆盖，实体机状态仍须如实记录。
- Vditor 保持 `3.11.3`。Vditor 私有 DOM 操作继续集中在 `src/renderer/vditor-adapter.js`。
- 保持 `contextIsolation: true` 和 `nodeIntegration: false`，不以 `--no-sandbox` 作为一般兼容方案。
- 本版本只完善本地 Markdown 文件编辑、桌面集成和安全边界，不扩展产品形态或数据模型。

## 3. 当前代码基线

以下结论用于规划路线，不等同于完成验收。每个批次开始前仍须核对当前源码。

### 3.1 已有基础

- 手动保存和自动保存都经过 renderer 的同一保存入口；成功后才更新保存基线和修改状态。
- 工作区已有单个 chokidar watcher，能够收到 `add`、`change` 和 `unlink` 事件。
- 外部修改已有标签 `!`、活动文档持久横幅、“放弃标签修改并重载”和“忽略外部更改”动作。
- 未解决外部修改或选择忽略后，自动保存会暂停。
- 主进程已有统一外部 URL allowlist，并用于 `openExternal`、`will-navigate` 和新窗口处理；常见危险 scheme 已有测试。
- preload 暴露的是明确方法，没有把底层 `ipcRenderer` 直接交给 renderer。
- `contextIsolation` 已开启，`nodeIntegration` 已关闭；主窗口 `sandbox` 目前关闭。
- Markdown 保存时已有集中恢复原始图片路径的 adapter 能力，普通 Markdown 不会保存内部 `local-file:` 地址。
- 设置持久化已有临时文件替换写入，但普通 Markdown 文档保存尚未复用安全写入能力。
- 项目已有 Vitest、Playwright、格式检查、lint、类型检查、Vditor 版本检查和构建脚本。

### 3.2 仍需完成或修正

- 普通文档仍直接写目标文件，没有统一的安全写入服务、无变化跳过和故障注入测试。
- 没有恢复快照服务；session 只保存工作区和已有路径的标签，也没有轻量 schema、大小限制和损坏快照处理。
- watcher 只覆盖当前工作区，工作区外独立打开的文件不受监控。
- 应用自身保存仍依赖固定 1.5 秒忽略窗口；文件 watcher 没有明确的写入稳定等待、正文比较和迟到异步结果失效规则。
- 外部删除只有短暂消息，未进入持久状态，自动保存可能重新创建文件。
- “忽略外部更改”后手动保存可直接覆盖磁盘，没有再次确认或另存动作。
- 目录重命名不会更新已打开的后代文件；目录删除不会统一处理后代标签。
- 大部分特权 IPC 没有校验调用来源，高风险参数运行时校验不完整，通道字符串分散。
- `local-file:` 可以读取任意已知绝对路径，没有随文档或工作区维护受控根，也没有规范路径、realpath、私有目录和资源响应类型限制。
- CSP 仍允许不安全脚本策略；关闭 sanitize 时没有明确风险提示。
- macOS 重建窗口时可能继承进程级关闭确认状态。
- 保存任何设置都会重建全部 Vditor，可能丢失撤销历史和选区。
- HTML/PDF 导出直接使用渲染 HTML，可能包含应用内部 `local-file:` 地址；PDF 隐藏窗口虽已启用 sandbox，但还没有自包含图片来源和完整隔离验证。
- 应用标识仍有不一致，Node.js 支持版本未声明，GitHub Actions 尚不存在。

### 3.3 与原计划相比的调整

- 原计划第 11 节“统一 URL 校验”已经基本实现，因此批次 8 是复核和补齐边界，不应重复重写。
- 原计划第 8 节的基础外部修改横幅已经存在；后续重点是完整动作、状态模型和测试。
- 原计划第 8.2 节的未保存对话框拖动已有可观察行为和部分测试；抽取 helper 只能在确有复用价值时进行，不单独为了重构施工。
- 设置重建已能保留模式和大致滚动位置；批次 13 应保留这些成果，重点消除展示类设置导致的无条件重建。
- 恢复、工作区外 watcher、删除冲突、IPC 来源验证、本地资源授权和 CI 当前仍是从零或接近从零建设。
- 各批次遵守开发计划第 4.1 节的组件契约：批次 1 产出安全写入结果和预期正文；批次 3 用稳定等待与正文比较消费它；批次 9 统一主 frame 校验和高风险参数验证；批次 10 维护本地资源受控根；批次 14 使用一次性内容快照和自包含图片来源。

## 4. 验证命令

按修改范围选择最小充分检查，批次结束前再执行约定的完整检查。

| 命令                   | 用途                                  |
| ---------------------- | ------------------------------------- |
| `npm run format:check` | Prettier 检查                         |
| `npm run lint`         | ESLint 检查                           |
| `npm run typecheck`    | main/preload TypeScript 类型检查      |
| `npm run check:vditor` | 确认 Vditor 固定版本与离线资产约束    |
| `npm test`             | Vitest 单元测试                       |
| `npm run build`        | 编译 main 并复制 renderer/Vditor 资产 |
| `npm run test:e2e`     | 构建并运行 Electron Playwright E2E    |
| `npm run check`        | 除 E2E 外的完整检查                   |
| `npm run check:all`    | `npm run check` 加 Electron E2E       |

规则：

- 同时影响 main/preload/renderer 或 renderer shell 的功能批次，完成前原则上运行 `npm run check:all`。
- 只改纯函数或文档时可以先运行针对性测试和 `npm run check`，但必须在阶段审查或发布准备时补齐 E2E。
- 发布打包不包含在日常 `check:all` 中。只在发布准备批次运行对应 `npm run release:linux:*`，并执行真实安装包冒烟测试。

### 批次 1：安全文档保存

**解决的问题：** 写入中断或替换失败不能截断原文件；手动保存和自动保存使用同一可靠写入路径，并为 watcher 留下可直接比较的预期正文。

**包含范围：** 单一安全写入服务、可注入文件系统操作、同目录唯一临时文件、完整写入与同步、关闭和替换、必要元数据、跨平台替换结果模型、失败清理、可理解错误、现有编码和行尾策略、无变化跳过落盘及保存成功后的预期正文更新。优先使用经过验证的原子写入库。

**不包含范围：** recovery、完整 watcher 重构、外部冲突新动作。

**必须证明：** 正常保存；临时写入失败原文件不变；替换失败原文件可读且标签仍未保存；成功无临时文件；权限不无故变化；CRLF/LF 不回归；自动保存经过同一服务；内容未变化时不替换文件或改变 mtime；保存后预期正文与实际磁盘正文一致。

**用户手测重点：** 普通保存、另存为、自动保存和一个由 Agent 提供的安全失败模拟。破坏性磁盘故障不要求用户手工制造。

**完成标准：** 针对性故障测试和 `check:all` 通过，或如实记录 E2E 环境限制；Tracker 记录最终替换语义、持久性边界、预期正文更新时机和跨平台未验证项，供批次 3 直接消费。

### 批次 2：未保存内容恢复

**解决的问题：** 异常退出后，无路径新文档和未保存修改不会永久丢失。

**包含范围：** 独立 recovery 存储、稳定文档 ID、正文与必要元数据、简单 schema 版本、必要字段和单快照大小限制、防抖和安全写入、损坏快照跳过、快照清理、启动时恢复/放弃、磁盘已变化时不静默覆盖，以及 recovery 目录的私有权限和不进入资源受控根的约束。

**不包含范围：** 批次 4-6 负责的外部冲突状态和文件树操作。

**必须证明：** Untitled 和已有文件的快照创建与恢复；正常保存和明确“不保存”后清理；放弃后不重复提示；损坏、超限或未知 schema 快照不会阻止应用启动；错误与日志不泄露完整正文；renderer 只能调用恢复候选、恢复和放弃接口；恢复遇到磁盘变化进入安全状态。

**用户手测重点：** 新建文档输入内容后强制结束应用，再启动并选择恢复；重复一次“放弃恢复”。

**完成标准：** 生命周期单测、真实 Electron 恢复 E2E 和 `check:all` 通过；存储位置、清理规则和隐私边界已记录。

### 批次 3：watcher 所有权与稳定内容读取

**解决的问题：** 工作区内外的打开文件都能被可靠监控，应用自己的保存不会被误判，监听资源可以释放。

**包含范围：** 工作区 watcher、去重的工作区外监听、标签关闭/另存/切换工作区/退出清理、批次 1 预期正文、连续事件合并、文件内容 watcher 的 `awaitWriteFinish` 或等价稳定等待、正文比较、规范路径边界，以及 watcher 的当前绑定和 disposed/cleanup 状态。目录 watcher 保持现有即时目录事件行为。

**不包含范围：** 完整冲突动作和目录重命名后的全部 UI 行为。

**必须证明：** 工作区内不重复监听；工作区外文件可检测；同一文件不重复监听；磁盘正文与预期保存正文相同的自身事件不提示冲突；即使仍在去抖时间内，正文不同的事件也不会被吞掉；mtime 相同不能掩盖正文变化；关闭、另存和重绑后旧 watcher 的 timer 与异步读取结果不会更新新状态；旧工作区事件不污染新工作区；路径大小写和符号链接行为有明确测试或限制记录。

**用户手测重点：** 分别打开工作区内文件和工作区外文件，用另一个编辑器修改并观察 Vditor Desktop。

**完成标准：** watcher 针对性测试和 `check:all` 通过；固定 1.5 秒窗口不再承担最终内容判断；Tracker 记录 watcher 去重方式、稳定等待、正文比较、当前绑定检查和清理路径。

### 批次 4：外部修改冲突完整流程

**解决的问题：** 外部修改和本地未保存内容相遇时，用户有完整且明确的选择，任何保存都不会暗中覆盖磁盘版本。

**包含范围：** 持久 modified 状态、磁盘版本信息、重载、另存当前内容、明确覆盖、忽略后的再次保存确认、重复外部变化、状态清理、必要的文档级提示复用。

**不包含范围：** 外部删除和目录级操作。

**必须证明：** 冲突期间自动保存暂停；忽略后普通保存仍要求确认；重载读取确认时的最新稳定内容；另存不修改外部版本；解决后保存基线和标记正确；多个同路径标签行为一致或受到明确约束。

**用户手测重点：** 用其他编辑器修改同一文件，分别走“重载”“另存当前内容”“确认覆盖”和“取消覆盖”。

**完成标准：** 状态转换单测、冲突 E2E 和 `check:all` 通过；三种语言的新增文案齐全。

### 批次 5：外部删除、重新出现与不可读状态

**解决的问题：** 文件在应用外被删除后不被自动保存偷偷重建，内存内容得到保护。

**包含范围：** deleted、reappeared 和必要的 unreadable/permission 状态；暂停自动保存；另存、保留 Untitled、关闭、经确认重建；文件重新出现后的明确决策。

**不包含范围：** 应用文件树主动删除和目录重命名的全部路径更新。

**必须证明：** 无论是否有本地修改，外部删除都不会静默重建；待处理内容和编辑模式仍在；重新出现不会静默覆盖内存；关闭和重建动作有正确确认；恢复快照不会绕过冲突。

**用户手测重点：** 分别删除一个干净文件和一个有未保存修改的文件，再测试文件重新出现。

**完成标准：** 删除状态单测、外部删除/重新出现 E2E 和 `check:all` 通过。

### 批次 6：重命名、删除与另存后的路径一致性

**解决的问题：** 文件树操作和另存后，标签、资源目录、最近文件和 watcher 指向同一真实位置。

**包含范围：** 文件及目录重命名的后代路径更新、`baseDir` 和相对图片、最近文件、应用内 rename/delete/Save As 期间 watcher 暂时解绑与完成后重绑、重绑后的磁盘正文确认、目录删除影响、Untitled 默认路径与工作区切换。

**不包含范围：** 新文件管理功能或文件树视觉改版。

**必须证明：** 重命名目录后所有打开后代仍可保存且图片正常；删除目录不会遗漏后代标签；脏标签不会被不透明地丢弃；另存后只监听新位置；应用内重命名不产生虚假删除冲突；重绑后如果磁盘正文与预期不同，仍进入正确外部变化流程。

**用户手测重点：** 打开含相对图片的文件，重命名父目录、另存到工作区外、删除所在目录，逐项观察标签和提示。

**完成标准：** 路径状态单测、文件树 E2E 和 `check:all` 通过。

### 批次 7：阶段 B 独立复核

**目标：** 不实现新功能，独立审查批次 1-6 的实际代码、提交和测试，寻找保存、恢复、watcher 与冲突之间的组合缺陷。

**重点：** 安全写入是否只有一个入口；无变化保存是否真的不落盘；短时去抖是否可能吞掉正文不同的外部变化；watcher 是否等待内容稳定并在 cleanup 后忽略迟到结果；删除状态是否可能被 recovery 或自动保存绕过；Save As 是否留下旧快照/监听；工作区切换是否有迟到事件；异常路径是否保持原文件和内存内容。

**完成标准：** 先输出按严重程度排序的问题清单；问题修复后运行 `check:all`；Tracker 记录审查结论、修复提交和剩余风险。

### 批次 8：导航与外部链接安全收尾

**解决的问题：** 复核现有统一 URL allowlist，补齐受信任 `app:` 页面边界和恶意输入测试。

**包含范围：** `window.open`、`will-navigate`、preload `openExternal` 的一致性；协议大小写、空白、编码、控制字符、畸形 URL；应用内部导航目标限制。

**不包含范围：** 泛化 IPC 校验和本地文件协议授权。

**必须证明：** 只允许明确支持的 `http:`、`https:`、`mailto:`；危险或无法解析 URL 被拒绝；Markdown 链接不能让主窗口导航到任意网页；现有相对 Markdown 跳转不回归。

**用户手测重点：** 正常网页链接和 `mailto:` 能交给系统处理，危险链接不产生应用内导航。主要证据应来自自动化测试。

**完成标准：** URL 单测、相关 E2E 和 `check:all` 通过；若现有实现已满足某项，只补测试或记录证据，不重复重写。

### 批次 9：IPC 来源与高风险参数校验

**解决的问题：** 特权调用只接受可信主 frame，并在 main 边界验证会产生文件、窗口、导出或 shell 副作用的高风险输入。

**包含范围：** 一个小型受信任主 frame helper；精确应用 origin、页面路径和主 frame 身份；高风险 handler 的路径、枚举、数字范围、长度/数量、对象结构和二进制载荷 validator；副作用前校验；稳定且可本地化的领域错误；main/preload/renderer 通道契约一致性。

**不包含范围：** 本地资源协议的授权模型和 CSP 定案。

**必须证明：** 非可信来源和子 frame 的特权调用被拒绝；来源校验不使用字符串前缀或模糊 host 匹配；畸形或超限参数在文件系统、对话框或 shell 副作用前被拒绝；合法调用保持兼容；preload 仍为窄 API；renderer 错误不泄露内部堆栈；高风险文件操作返回可处理的领域错误。

**用户手测重点：** 正常打开、保存、重命名、删除、设置、导出和窗口控制。恶意输入由测试完成。

**完成标准：** IPC 边界测试和 `check:all` 通过；Tracker 记录主 frame helper、已覆盖的高风险 handler、validator 和错误契约；集中通道/类型定义时避免无关的大规模迁移。

### 批次 10：本地资源受控根与响应边界

**解决的问题：** Markdown 不能借助 `local-file:` 探测、读取或执行当前文档目录/工作区之外的内容。

**包含范围：** 当前工作区根和工作区外已打开文档目录组成的受控根集合；打开/关闭时增删；URL 词法检查；URL pathname 到本地路径的跨平台转换；规范化、realpath、目录边界和符号链接逃逸；TOML 配置、Chromium user data、recovery 不得注册为资源根；不存在与未授权的中性失败；内联资源类型 allowlist、准确 `Content-Type`、`nosniff`、主动/未知类型拒绝；SVG 采用“验证后允许，否则拒绝”的策略；合法相对图片和粘贴图片兼容。普通文件操作继续使用各自的窄 IPC 和参数校验。

**不包含范围：** CSP 最终策略和导出内容修正。

**必须证明：** 合法资源按正确类型可读；越界、`..`、无效编码、反斜杠、绝对路径注入、符号链接、私有目录和不存在路径被拒绝且不泄漏存在性；关闭文档/工作区后对应根失效；HTML、JavaScript、XML 和未知类型不能内联执行；若保留 SVG，真实 Electron 测试证明其不能执行脚本或导航，否则本版本明确拒绝；Windows 路径转换和 junction 输入有纯测试。

**用户手测重点：** 工作区图片、工作区外独立文档的相对图片、粘贴图片仍可显示。

**完成标准：** 路径/协议/响应头测试、图片与主动内容 E2E 和 `check:all` 通过；Tracker 记录受控根来源、增删时机、私有目录和响应类型策略。

### 批次 11：sandbox、CSP 与 sanitize 定案

**解决的问题：** 在真实 Vditor/Electron 组合中验证并尽量收紧 renderer 防线，而不是只切换配置开关。

**包含范围：** 主窗口 sandbox 兼容实验、CSP 中 unsafe 指令的真实依赖、Markdown sanitize 默认行为、关闭 sanitize 的风险提示、恶意 HTML 测试、最小替代措施和安全说明；复核批次 10 的资源响应限制与 renderer CSP 能共同阻断主动内容，而不是彼此留下缺口。

**不包含范围：** Vditor 升级或 renderer 框架迁移。

**必须证明：** `contextIsolation` 保持开启、`nodeIntegration` 保持关闭；sandbox 结果由真实 Electron E2E 支持；可移除的 CSP 权限已移除；不能移除的有最小复现和风险记录；sanitize 开关行为清楚。

**用户手测重点：** 三种编辑模式、图片、链接、粘贴和导出没有明显回归；安全结论主要由 Agent 提供证据。

**完成标准：** 最小实验、恶意内容测试和 `check:all` 通过；无法完成的加固有明确限制与替代措施，不能静默跳过。

### 批次 12：macOS 窗口关闭确认状态

**解决的问题：** 一个窗口的关闭确认不能让以后创建的窗口绕过未保存提示。

**包含范围：** 按窗口或创建周期管理确认状态；正常关闭、取消、保存后关闭和不保存关闭。

**不包含范围：** 多窗口产品功能或 macOS 打包发布。

**必须证明：** 纯状态测试可在 Linux 运行；现有单窗口关闭流程不回归；未在 macOS 实机执行时明确标注未验证。

**用户手测重点：** Linux 只做普通未保存关闭；若有 macOS 环境，再测试关闭后点击 Dock 重建窗口。

**完成标准：** 状态单测、可用环境中的集成验证和 `check:all` 通过。

### 批次 13：设置热更新与编辑状态保护

**解决的问题：** 外观和布局设置不应重建所有编辑器并清空撤销历史。

**包含范围：** 设置分类、展示/布局热更新、Vditor 可安全更新项、真正需要重建的选项、重建时沿用已有模式/滚动保护并评估选区限制。

**不包含范围：** 设置页视觉重做或全部 renderer 重构。

**必须证明：** 主题、字体、缩放、工具栏和侧边栏等约定项目不破坏撤销；重建只发生于有证据必须重建的设置；现有模式和滚动行为不回归。

**用户手测重点：** 输入文字，修改各类展示设置，然后执行撤销并确认编辑历史仍在。

**完成标准：** 分类测试、真实撤销 E2E 和 `check:all` 通过；Tracker 记录哪些设置仍需重建及原因。

### 批次 14：HTML/PDF 导出来源与隔离能力

**解决的问题：** 导出文件不包含只在应用内部有效的地址，PDF 生成窗口也不继承编辑窗口的 preload 或文件能力。

**包含范围：** HTML 与 PDF 共用原始图片来源转换；导出开始时建立一次性内容快照；HTML 恢复可移植的原始/相对图片来源；PDF 把本地图片转换为 data URL 或等价的自包含来源；PDF 隐藏窗口无业务 preload、保持 `nodeIntegration: false` 和 `contextIsolation: true`、可行时启用 sandbox，并禁止新窗口和非预期导航；相对图片测试；导出主题行为的明确说明。

**不包含范围：** 全新导出格式或主题系统重做。

**必须证明：** 导出 HTML/PDF 不含 `local-file:` 或 `app://`；包含相对图片的 HTML 在约定目录结构中可打开，PDF 图片可见；隐藏窗口不能打开新窗口、导航到非预期页面或调用主窗口业务 preload；普通 Markdown 保存和编辑器预览不回归。

**用户手测重点：** 导出包含相对图片的 HTML 和 PDF，在应用外打开并确认图片结果符合 Agent 说明。

**完成标准：** 导出内容与窗口隔离的自动化测试、Linux 实际导出手测和 `check:all` 通过；Tracker 记录 HTML/PDF 图片转换和隐藏窗口配置。

### 批次 15：应用标识、Node 与依赖一致性

**解决的问题：** 包配置、Linux metadata、运行时要求和依赖安装策略可复现且互相一致。

**包含范围：** 应用 ID/名称统一、Node.js `engines` 与文档/CI 对齐、依赖 engine 警告、Electron 声明与执行许可、lockfile、既有 Linux 工具固定与校验。

**不包含范围：** Windows/macOS 签名、自动更新或 Vditor 升级。

**必须证明：** 干净安装使用受支持 Node 版本；构建与 Vditor 固定检查通过；Linux desktop/AppStream/builder 身份一致；发布工具版本和 SHA-256 校验保留。

**用户手测重点：** 通常无需单独 UI 手测；安装包验证放在批次 16。

**完成标准：** 配置检查、`npm run check` 和构建通过，支持范围写入 README。

### 批次 16：CI、文档与 Linux 发布候选

**解决的问题：** 每次提交自动执行发布门槛检查，并形成可人工验证的 0.2.0 Linux 候选版本。

**包含范围：** GitHub Actions、Xvfb E2E、README/README_CN、CHANGELOG、ISSUES、安全说明、版本号、Linux 候选包和冒烟测试记录。

**不包含范围：** Windows/macOS 实体机发布、签名、自动更新。

**必须证明：** CI 能区分启动环境失败和断言失败；`check:all` 通过；候选包能打开、编辑、保存、恢复和导出；新增的保存故障、recovery 损坏、watcher 迟到读取、IPC 来源/参数、路径绕过、主动资源和隔离导出测试均进入 CI；未验证平台如实记录。

**用户手测重点：** 使用候选安装包完成打开、编辑、保存、异常恢复、外部冲突和导出冒烟路径。

**完成标准：** CI 绿色、文档与实际行为一致、Linux 候选包手测通过。发布前最后更新 `docs/01-CODE-STRUCTURE.md`，使其反映最终代码。

### 批次 17：0.2.0 最终独立审查

**目标：** 不实现新功能，逐项对照原计划第 25-27 节发布门槛，独立验证代码、测试、提交和文档，而不是相信 Tracker 状态。

**重点：** 高风险失败路径、跨批次状态组合、安全写入与预期正文、watcher 稳定等待/正文比较/cleanup、IPC 主 frame 与高风险参数、资源受控根与主动内容响应、文档/工作区关闭后的根撤销、PDF 隐藏窗口隔离、实现是否符合开发计划第 4.1 节的组件契约、测试是否只验证表面现象、未验证平台是否被夸大、生成物和本地配置是否误入 Git。

**完成标准：** 先给出按严重程度排序且带文件/测试依据的问题；所有阻塞问题解决；`check:all`、Linux 候选包冒烟和最终文档检查有可核验证据。

## 7. 对话模板

### 7.1 新 Session：默认自主执行

```text
我们继续 Vditor-Electron 0.2.0 开发，当前进行批次 <批次编号>。请阅读 docs/13-0.2.0-EXECUTION-TRACKER.md，并按其中的自主执行流程、按需阅读规则和当前批次施工卡完成任务。
```

这句话已经授权 Agent 在当前批次范围内检查、实现、测试、更新 Tracker 和提交，不需要再发送“方案通过”。Agent 必须在开始时用简短进度说明告知当前理解和首要步骤，但不得停下来等待例行批准。

### 7.2 需要先看方案的特殊情况

如果某个批次风险较高，用户也可以临时改用审批模式：

```text
当前进行批次 <批次编号>。按 Tracker 的按需阅读规则检查现状，但本轮先不要修改或提交。请给我简短施工方案、范围、验证方式和需要我决定的问题，然后停止等待确认。
```

方案通过后发送：

```text
方案通过。现在恢复 Tracker 的自主执行流程，完成当前批次并按规定汇报，不进入下一批次。
```

### 7.3 Agent 何时应询问用户

Agent 只在以下情形使用交互式问答，并尽量给出少量、易懂、有明确影响的选项：

- 存在多个会产生不同用户行为的合理方案。
- 必须扩大当前批次范围才能安全完成。
- 用户或其他 Agent 的现有修改与本任务直接冲突。
- 需要执行原计划未授权的破坏性操作、依赖升级或架构变更。
- 已自行排查但仍存在无法继续的真实阻塞。

普通实现取舍、代码组织、测试失败和可自行验证的技术问题不应转交给用户。

### 7.4 要求 Agent 改写手测步骤

第 8 节已要求 Agent 主动提供手测步骤。如果汇报仍过于技术化，发送：

```text
请把本批次需要我完成的手动验证改写成普通用户可执行的步骤。每项都写清楚：
1. 测试前需要准备什么；
2. 我要点击或输入什么；
3. 正常情况下应该看到什么；
```

## 8. Agent 完工汇报要求

每个自主执行批次完成后，Agent 的最终汇报至少应包含：

1. **完成内容：** 用用户能理解的语言说明行为变化，而不只是列文件。
2. **范围差异：** 与施工方案或原计划不同之处及原因。
3. **失败场景证据：** 哪些故障、权限、安全或竞态由什么测试证明。
4. **验证结果：** 每条命令的通过、失败或未运行状态；E2E 环境限制单列。
5. **提交：** commit hash 和 message；有意保留的未提交修改。
6. **遗留问题：** 风险、平台未验证项和后续批次注意事项。
7. **手动测试：** 准备、操作、预期结果、失败表现和清理方式。

不能接受以下表述作为完成证据：

- “代码已实现，理论上可以工作。”
- “测试应该能通过。”
- “Linux 通过，所以三平台均已支持。”
- “已有 try/catch，所以失败安全。”
- “构建成功，所以 E2E 已验证。”
- 只列修改文件，不说明用户行为和失败路径。
